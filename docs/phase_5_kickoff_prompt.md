## Правила разработки

1. **Спеки — источник истины.** Код строго соответствует `specs/`. Любое отклонение оформляется как «предложение изменения спека» и применяется только после согласования.
2. **DoD задачи:** код по спеку (BR/UC); unit-тесты на затронутые BR; миграция (если есть) применяется на пустой БД; нет N+1 и лишних запросов; UI на токенах `packages/ui`; коммит ссылается на задачу и BR.
3. **Перед каждым коммитом:** `pnpm typecheck && pnpm lint && pnpm test && pnpm build` — все exit 0. Красное не коммитить.
4. **Версионирование (ПРОЦ-02):** SemVer; Фаза 5 — **minor**, релиз `v1.3.0`. Тег на `main`, версия в футере берётся из `docker-compose.yml` (build arg `VERSION`) — при выпуске поднять там и в `.env.example`.
5. **Доставка:** короткие коммиты в `main` + `git push` (агент пушит сам). Перед пушем прогонять полный пайплайн.
6. **Локальная БД недоступна** (peer-auth, нет sudo), поэтому проверяются только unit-тесты, typecheck и build; миграции и сид — на VPS. Не утверждать, что что-то проверено вживую, если это не так.
7. **Ручное тестирование выполняет пользователь.** Агент готовит план, задания и фиксирует результаты.

## Уроки Фазы 4 (не повторять)

1. **Права роли должны точно соответствовать 00 §4.2.** В Фазе 4 нашлось, что у роли ОПР было право `production_order:confirm` — Оператор мог подтверждать и отменять ПЗ, вводить за Оператора, корректировать факт.
2. **Атрибуция аудита — по праву действия.** Переходы ПЗ пишутся с правом того действия, которым вызваны (`production_order:accept` при подтверждении получения, `report` при внесении итога, `confirm` при вводе за Оператора). Иначе kernel `writeAudit` падает с «No role has permission …» прямо в интерфейсе.
3. **Хронометраж:** одна запись на переход; записи без смены статуса (корректировка факта, Р-18) не создаются; длительности считаются **раздельно** по сущностям (документ и строка РЦ).
4. **Страницы под правами отдают «Доступ запрещён»**, а не 500 (`components/access-denied.tsx` + `lib/auth/page-guard.ts`); загрузчики данных проверяют права и «свой РЦ».
5. **Кнопки действий закрываются правами** — иначе роль видит чужие действия (кнопка создания ПЗ у С1С).
6. **Клиентские обработчики показывают ошибку**: не закрывать диалог до установки текста ошибки.
7. **Списки — серверные поиск и пагинация** (образцы: `nsi/products/queries.ts`, `notifications/queries.ts`, `audit/queries.ts`, `timing/queries.ts`), без `count` на каждый запрос; клиентская фильтрация не используется.
8. **Файл конфига nginx нельзя копировать целиком** — в нём блок `listen 443 ssl` от certbot; для SSE достаточно вставить `location /api/events/`.
9. **Хелперы и типы — только в обычных модулях:** ничего синхронного из файлов с `'use server'` не экспортировать; запросы данных в `'use server'`-файлах не держать.

## Правила коммуникации

- Язык — **русский**.
- **Формат работы (строго, `process.md` §4.2.1):** агент выдаёт **ровно одно задание** (действие → ожидаемый результат → что прислать) и **ждёт ответ**. Никаких списков задач «на будущее» и «заодно проверьте» в одном сообщении. Результат ОК — следующее задание; не ОК — сначала разбираемся с текущим.
- **Команды для VPS** — один блок на одно задание; пользователь выполняет и возвращает вывод. Агент не имеет доступа к серверу.
- **Дефекты:** критичные (блокируют работу или искажают данные) — исправляем немедленно; некритичные — сразу после обнаружения (как договорено в Фазе 4), с пометкой в отчёте о тестировании.
- **Отчёты** — по форматам `process.md` §6: самопроверка фазы, релиз-отчёт, отчёт о ручном тестировании (для Фазы 5: `docs/phase_5_selfcheck_report.md`, `docs/release_v1.3.0_report.md`, `docs/release_v1.3.0_test_plan.md`, `docs/release_v1.3.0_test_report.md`).
- Перед утверждением о содержимом файла — **прочитать файл**. При неясности — задать вопрос, не догадываться.

## Редеплой на VPS (проверенная процедура)

```bash
cd /opt/prodtrack
git fetch origin && git pull origin main
git log -1 --oneline
docker compose down
docker compose build --no-cache
docker compose up -d
sleep 25
bash scripts/postdeploy-check.sh
```

Особенности (проверено на практике):

1. Версия в футере встраивается **на этапе сборки** (`next.config.js` → `env.VERSION`), поэтому после подъёма версии нужен `build --no-cache`; правка `.env` без пересборки не влияет.
2. Миграции и сид в контейнере запускаются **не** через `pnpm --filter` (в standalone-образе нет воркспейса), а так:
   ```bash
   docker compose exec -T web sh -lc 'prisma migrate deploy --schema=/app/packages/db/prisma/schema.prisma'
   docker compose exec -T web sh -lc 'cd /app/packages/db && tsx prisma/seed.ts'
   ```
3. `docker compose down` удаляет логи: если разбираем ошибку — снять `docker compose logs --tail=50 web` **до** перезапуска.
4. Сервер общий (соседи: `mes-midex.factoryall.ru`, `tracker.factoryall.ru`) — ничего лишнего не трогать, после деплоя проверять их доступность.
5. Права проверяются кодом (`packages/contracts`), поэтому сид на работоспособность не влияет — он нужен, чтобы новые коды прав отображались на экране «Роли».
