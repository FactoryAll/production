# Отчёт «Дисциплина закрытия ПЗ» — постановка (T-100)

Статус: **постановка**, код не начат. Ждёт ответов главной линии по §7 (четыре вопроса).
Причина, по которой постановка идёт первой: по отчётам у нас уже дважды разъезжались
определения (ОПЭ-70 — режим «Смена» терял дату, ОПЭ-71 — «День» игнорировал «По дату»),
и постановка ловит такое дешевле, чем проверка на стенде.

Источник: бэклог `tasks.md` T-100 — «незакрытые ПЗ, по каким РЦ, сколько дней висят»
(решение владельца 26.10.2026 «остальные в отбор»).

## 1. Зачем

ПЗ закрывается автоматически, когда последняя строка отчиталась. Пока этого не случилось,
документ висит: продукция в системе не учтена как выпущенная, задача для 1С не создана,
следующая смена по этому РЦ планируется «вслепую». Владелец уже просил напоминание НП —
оно есть (ОПЭ-60), но показывает **только число и список** на экране НП.

Отчёт отвечает на другой вопрос: **сколько висит, где именно, и кто не отметился**. Это разрез
по РЦ и строкам, с днями и с выгрузкой, чтобы можно было вернуться к разговору с цехом, а не
только «увидеть и забыть».

## 2. Определения — не выдумываем заново

В системе уже есть правило просрочки, введённое решением владельца 26.10.2026 (ОПЭ-60) и живущее
в `apps/web/src/app/notifications/overdue-queries.ts`. Отчёт **обязан** использовать его же,
иначе у НП будет напоминание «с 14-го», а в отчёте — другой счёт на ту же смену.

| Понятие | Правило | Источник |
|---|---|---|
| Срок | дата смены + 1 календарный день (нормальный допуск) | ОПЭ-60 |
| Просрочено (висит сверх срока) | дата смены + 2 календарных дня и больше | ОПЭ-60, `getOverdueOrders` |
| Дней висит | целые календарные дни от даты смены до сегодня | `daysSinceShift` |
| Закрытое ПЗ | `ProductionOrder.status = COMPLETED` | авто-закрытие `checkAndCloseProductionOrder` |
| «В работе» (висящее) | `DRAFT`, `CONFIRMED`, `IN_PROGRESS` | остальные статусы |
| Отменённое | `CANCELLED` | в отчёт не входит |

Правило «закрытое» особое: `COMPLETED` ставится автоматически, когда **все** строки `REPORTED`.
Отдельного действия «закрыть ПЗ» в системе нет — это важно для формулировок отчёта: висит не
«тот, кто забыл нажать кнопку», а «тот, где не отчитались строки».

## 3. Из чего складывается

Одна строка отчёта — **ПЗ** (документ), а не строка РЦ: вопрос дисциплины задаётся про документ,
а внутри видно, какие РЦ не отметились.

| Колонка | Значение | Источник |
|---|---|---|
| ПЗ | короткий идентификатор, ссылка на карточку | `ProductionOrder.id` |
| Смена и дата | номер и дата смены | `Shift.number`, `Shift.date` |
| Статус | Черновик / Подтверждено / В работе | `ProductionOrder.status` |
| РЦ | перечень РЦ ПЗ с отметкой по каждому: «03 — отчитался», «05 — не отчитался» | `ProductionOrderLine.status` |
| Строк / отчиталось | «2 / 3» | счётчики по строкам |
| Операторы | ФИО по строкам, у кого нет — «—» | `ProductionOrderLine.operator` |
| Висит, дней | от даты смены до сегодня | `daysSinceShift` |
| Просрочено | да/нет по правилу ОПЭ-60 | дата смены + 2 дня |
| Последнее изменение | когда ПЗ менялось в последний раз | `ProductionOrder.updatedAt` |

Итоги за период: **сколько ПЗ висит**, из них **просрочено**, **максимум дней**, разбивка
**по РЦ** (у какого РЦ больше всего незакрытых строк).

## 4. Экран и фильтры

Страница `/reports/closure-discipline`, раздел «Отчёты» (пункт в списке отчётов добавляется).

- **Период по дате смены** — та же форма, что у остальных отчётов (`PeriodForm`), включая
  исправленные режимы: «Месяцы» из данных, «День» как диапазон, «Неделя» списком недель,
  «Смена» списком смен. Своих фильтров отчёт не изобретает.
- **Только висящие / все** — переключатель: по умолчанию **только висящие** (иначе отчёт
  смешивает закрытые и незакрытые и перестаёт отвечать на свой вопрос).
- **Порог**: по умолчанию 2 дня (правило ОПЭ-60); возможность показать «все, включая свежие»
  — тот же переключатель.
- Фильтр по РЦ — как в остальных отчётах (селект).
- Таблица с итогами, просроченные строки подсвечены.

## 5. Выгрузка

CSV для Excel (`;`, BOM) — те же колонки и итоги, что на экране, по тем же параметрам адреса.
Выгрузка строится тем же `reportPeriodQuery`, что остальные отчёты, — чтобы не повторить ОПЭ-70.

## 6. Права

`reports:read` — НП, ОТК, АДМ, С1С (как у остальных отчётов). Напоминание НП (ОПЭ-60) остаётся
как есть: отчёт его **не заменяет** и не меняет.

## 7. Вопросы к главной линии (нужны ответы до кода)

1. **Разрез**: строка отчёта — ПЗ целиком (рекомендую) или строка РЦ, как на доске контура?
   ПЗ-целиком отвечает на «документ висит», строка РЦ — «где именно застряло»; в моём варианте
   оба ответа есть в одной строке (перечень РЦ с отметками), но таблица получается шире.
2. **Порог**: фиксированные 2 дня по правилу ОПЭ-60 или поле «показывать висящие больше N дней»
   с значением по умолчанию 2? Второе гибче, но добавляет ещё один параметр к периоду.
3. **Отменённые ПЗ**: не показывать вовсе (рекомендую — это не работа, а отмена), или отдельной
   строкой с пометкой, чтобы владелец видел, что документ был и отменён?
4. **Разрез по операторам**: нужен ли отдельный блок «кто не отчитался по своим строкам» —
   или достаточно колонки «Операторы» в строке ПЗ? Первое полезно для разговора с цехом,
   второе дешевле; предлагаю начать с колонки.

Каждый этап — с тестами, которые падают без правки; перед коммитом полный прогон
`typecheck`, `lint`, `test`, `build`.

## 9. Чего отчёт не делает

- не меняет напоминание НП и не закрывает ПЗ;
- не показывает закрытые ПЗ в основном срезе (только по переключателю «все»);
- не считает отменённые ПЗ работой;
- не вводит своих определений срока — берёт ОПЭ-60.
