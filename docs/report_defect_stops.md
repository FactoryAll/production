# Отчёт «Брак и простои» — постановка (T-101)

Статус: **постановка**, код не начат. Ждёт ответов главной линии по §7. Причина та же:
определения в отчётах у нас уже дважды разъезжались (ОПЭ-70, ОПЭ-71), и постановка ловит
это дешевле проверки на стенде.

Источник: бэклог `tasks.md` T-101 — «причины, часы, распределение по РЦ» (решение владельца
26.10.2026 «остальные в бэклог»).

## 1. Зачем

Два вопроса владельца: **почему брак** и **сколько стоит простой**. Сейчас в системе есть
количество брака и простои в факте, но причин не видно нигде: «Выпуск по РЦ» (T-095) показывает
только количество брака по цеху, а причины брака и простои не показывает вообще.

## 2. Чего здесь нового, а чего уже достаточно — честно

| Что | Где уже есть | Что даёт этот отчёт |
|---|---|---|
| Брак, штуки/кг по РЦ | **T-095 «Выпуск по РЦ», колонка «Брак»** | не главное здесь: показываем для контекста и доли |
| **Причины брака** | нигде | главное: разрез по справочнику `DefectReason` |
| **Простои: число и часы** | нигде | главное: `stopsCount`, `stopsDurationMinutes` по РЦ |
| Доля брака к выпуску | нигде (в T-095 только процент выполнения плана) | доля по категории, как в T-097 |

Вывод: отчёт **не дублирует T-095** только пока в нём есть причины брака и простои. Если
из отчёта убрать причины и простои — его делать не нужно, хватит T-095. Это записывается
прямо, чтобы отчёт не превратился в «ещё одну таблицу про брак».

**Сравнение с двумя другими отчётами партии — прямо:**

| Отчёт | Про что | Пересечение с T-101 |
|---|---|---|
| **T-100 «Дисциплина закрытия ПЗ»** | сколько висят незакрытые ПЗ, дни, какие РЦ не отметились | **нет**: T-100 про сроки документов, T-101 про качество работы. Одна и та же смена может быть в обоих, но вопросы разные |
| **T-097 «Выработка по сотрудникам»** | выпуск на человека по категориям + брак по категориям | **в браке по категориям** — числа совпадут (один источник), но разрез другой: T-097 по людям, T-101 по РЦ и по причинам. **Брак на человека в T-101 не делаем** — он уже в T-097. Простои на человека — новое (ниже), но это не дубль: в T-097 простоев нет вовсе |

Итог: T-101 не дублирует ни T-100, ни T-097. Единственное настоящее пересечение — сумма
брака по категориям, и это нормально: два отчёта могут показывать одно и то же число в разных
разрезах, но не должны показывать **один и тот же разрез**.

## 3. Определения

### 3.1. Брак

- единица — строка факта (`ProductionFact`): `defectQuantity` по категории факта
  (Масса / ГП / ПФ), как в T-095 и T-097;
- брак **не вычитается** из выпуска — в системе `quantity` и `defectQuantity` раздельны,
  склад принимает `quantity`;
- **доля брака** считается внутри категории (`брак / выпуск × 100`), не от суммы разных единиц;
- причина — `defectReasonId` факта. Ввод требует причину при браке (`Укажите причину брака`
  в трёх местах ввода), но исторические данные могут содержать брак без причины, поэтому
  в отчёте есть строка **«без причины»** — иначе такая доля брака «пропадёт» из разреза.

### 3.2. Простои

- `stopsCount` — число остановок, `stopsDurationMinutes` — длительность, обе величины в факте;
- **часы** — производная от минут (сумма минут / 60, два знака). Храним минуты, показываем
  и минуты, и часы: «12 остановок · 4,5 ч» читается, а «270 минут» требует счёта в голове;
- простои считаются по строкам ПЗ и их РЦ; к категории продукции не привязаны — факт ГП и ПФ
  одной строки может нести простои дважды, и это надо решить (§7, вопрос 2).

**Часы простоя на РЦ.** Сумма `stopsDurationMinutes` по строкам этого РЦ за период, делённая
на 60. Структурно — как брак по РЦ: разрез по цеху, без разбивки по людям.

**Старые данные: если основной факт пуст.** Показывать ноль в этом случае значило бы «потерять»
простой. Поэтому правило такое: значение берётся с основного факта; если там пусто, а в других
фактах строки минуты есть — берём **максимум** по ним (это дубли одного события, сумма дала бы
двойной счёт) и считаем такую строку отдельным счётчиком **«строк с простоем в неосновном
факте»**. Счётчик виден в подписи под таблицей и в CSV: цифра показывает, что данные
не потеряны, а объясняют, откуда значение. «Основной факт» при этом остаётся один —
`pickPrimaryFact`; max применяется только внутри строки как страховка для истории.

**Часы простоя на человека (предложение, прошу утвердить).** Простой принадлежит **строке**,
а не человеку: система не знает, кто именно стоял. Поэтому предлагаю приписывать простой
строки её **оператору** — он ведёт смену и вносит простой; работникам не приписывать, потому
что делить нельзя, а зачитывать каждому весь простой строки (как выпуск в T-097) значило бы
показывать двум людям один и тот же час простоя и складывать его в итог. Строка без оператора
даёт строку **«Без персональной привязки»** — тот же приём, что в T-097, иначе итог по людям
не сойдётся с простоем по РЦ.

### 3.3. Период

По **дате смены**, как во всех отчётах. Форма периода общая.

## 4. Что показываем — два разреза

**Разрез «По РЦ»** (основной, как просил владелец):

| Колонка | Значение |
|---|---|
| РЦ | код и название |
| Выпуск | Масса / ГП / ПФ (для контекста) |
| Брак | Масса / ГП / ПФ |
| Доля брака | по категориям, где есть выпуск |
| Остановок | число |
| Простой | минуты и часы |

**Разрез «По причинам брака»**:

| Колонка | Значение |
|---|---|
| Причина | код и название из `DefectReason`, плюс строка «без причины» |
| Брак | по категориям |
| Доля в браке | сколько эта причина составляет от всего брака периода |
| РЦ | в каких РЦ встречалась (перечень кодов) |

Итоги: всего брака по категориям, всего остановок, всего часов простоя, брак без причины.

## 5. Экран, выгрузка, права

- `/reports/defect-stops`, пункт в списке отчётов;
- переключатель разреза «По РЦ | По причинам» (одна страница, два разреза — не две страницы);
- период общий; фильтр РЦ не нужен для разреза по РЦ (он сам разрез), но нужен для разреза
  по причинам — предлагаю один фильтр РЦ в шапке, действующий на оба;
- выгрузка CSV (`;`, BOM) **одним файлом** с колонкой «Разрез» — по образцу T-097;
- права: `reports:read`.

## 6. Отменённые и незакрытые

Как в T-097: отменённые ПЗ не входят; незакрытые с фактом входят (факт — уже произошедшая
работа); строки без фактов вклада не дают.

## 7. Вопросы к главной линии (нужны ответы до кода)

1. **Два разреза на одной странице с переключателем** (рекомендую) или два отдельных отчёта?
   Переключатель дешевле и не плодит пункты в списке отчётов.
2. **Простои на ГП-РЦ дублируются**: у строки два факта (ГП и ПФ), оба могут нести
   `stopsDurationMinutes` — считать по строке один раз (рекомендую: сумма по строке) или
   по фактам (тогда простой одной строки посчитается дважды)?
3. **Брак без причины**: показывать строкой «без причины» (рекомендую) или это признак
   дефекта данных и такие факты надо вынести отдельно как замечание?
4. **Простой на человека**: приписывать оператору строки (рекомендую), или показывать
   и работникам «весь простой строки каждому» (тогда, как и выпуск в T-097, сумма по людям
   будет больше итога, и это придётся объяснять второй раз)?
5. **Нужен ли разрез по номенклатуре** (какой товар чаще бракуют) — или достаточно по РЦ
   и по причинам? Рекомендую пока не делать: в T-102 уже есть выпуск по номенклатуре, а брак
   по товару — следующий шаг, если владелец попросит.

## 9. Проверяемые свойства (пойдут в тесты)

1. Доля брака считается внутри категории и не смешивает кг со штуками.
2. Брак без причины попадает в отдельную строку и не теряется.
3. Простои одной строки не удваиваются при двух фактах (ГП и ПФ) — если выбран вариант §7.2.
4. Отменённое ПЗ не даёт ни строки, ни брака, ни простоев.
5. Факт на незакрытом ПЗ учитывается.
6. Сумма брака по причинам равна общему браку периода (включая «без причины»).
7. Простой на человека приписывается оператору строки; строка без оператора попадает
   в «Без персональной привязки», и итог по людям сходится с простоем по РЦ.
