# «ГП ↔ Масса»: разбор перед реализацией

- **Статус:** исследование, кода нет. Решение о реализации — за владельцем.
- **Дата:** 19.11.2026 · линия `ctrl-prod`
- **Требование владельца (дословно):**
  1. «одна Масса на ГП»;
  2. «что делать с ГП без привязки — выводить такой список с возможностью выбора массы. Также нужна для админа и НП сводная по всем привязкам ГП ↔ Масса с возможностью корректировки»;
  3. «должен быть множественный выбор РЦ, на которых можно фасовать ГП».
  Итог: «конкретное ГП должно потреблять (сейчас есть необязательный выбор) только одну Массу и может фасоваться на различных РЦ».

## 1. Как устроено сейчас

**Потребление — свободный выбор.** Правило живёт в `apps/web/src/lib/consumable-stock.ts`; список для оператора строит `getConsumableStock` — «всё, что лежит на Производственном складе категориями Масса и ПФ, с остатком больше нуля». Для ГП-строки оператор может выбрать **любую** Массу и **только ПФ своей номенклатуры** (`assertConsumptionMatchesLineProduct`). На РЦ 13 («Маркировка ЧЗ») Масса запрещена вовсе, а выпуск — только ГП (`consumptionCategoriesForWorkCenter`, `producesPf`).

**Три пути ввода, одно правило.** Потребление пишут: исполнение смены (`shift-execution/actions.ts`), «Ввод за Оператора» (`validateSubstitutionInput`) и корректировка факта НП (`correctProductionFact`). С 18.11 все три зовут общий `assertConsumptionWithinStock` — «больше остатка нельзя» (`ОПЭ-83`).

**Выбор РЦ для ГП — один флаг.** `WorkCenter.producesMass` (вычисляется по коду: 01, 02 — да) делит РЦ на «производящие Массу» и «все остальные». Форма ПЗ фильтрует номенклатуру так: РЦ Массы → только «Масса», иначе → только «ГП» (`apps/web/src/app/production-orders/new/_client-form.tsx` и `edit/_client-form.tsx`). С 19.11 к этому добавлено: на РЦ 13 — только ГП с остатком ПФ.

**Привязки ГП ↔ Масса в системе нет.** Ни поля, ни таблицы, ни экрана: связь существует только как след в истории фактов. В 1С уходят **фактические** данные — выпуск и потребление по РЦ (`lib/onec/task-data.ts`); спецификация/привязка не уходит и не принимается.

## 4. Риски

**R1. Привязки нет у 176 из 197 ГП — и взять её неоткуда.** Это главный риск: правило «одна Масса» без данных превращается либо в запрет планировать почти всю номенклатуру, либо в формальность. Смягчение: правило действует только для ГП с привязкой, остальные идут по старому и попадают в рабочий список «ГП без привязки». Строгий режим включается отдельным решением, когда список опустеет.

**R2. Кто владелец данных.** Привязка — это спецификация изделия, то есть мастер-данные. Если её ведут НП руками, 197 × 23 — ручная работа с ошибками; если из 1С — нужен канал импорта, которого нет. Решение владельца обязательно (вопрос 4).

**R3. РЦ фасовки — новый разрез, третий по счёту.** Сегодня «можно ли планировать ГП на РЦ» решает флаг `producesMass`; появится «ГП × РЦ». Риски: (а) пустой список = ГП нельзя запланировать нигде, а причина не видна; (б) существующие ПЗ ссылаются на РЦ, которых может не оказаться в списке — история должна остаться читаемой; (в) правило РЦ 13 («только ГП с остатком ПФ», выложено 19.11) складывается с новым фильтром, и пустой список должен объясняться, а не молчать; (г) план/факт по отчётам группируется по РЦ — если одна ГП идёт по нескольким РЦ, план «размазывается», и это надо принять осознанно.

**R4. Три пути ввода — риск повторения `ОПЭ-70/71` и `ОПЭ-83`.** Правило, поставленное только в форме, будет обойдено «Вводом за Оператора» и корректировкой НП. Проверять надо на сервере и во всех трёх путях, иначе получим ровно тот дефект, который чинили дважды.

**R5. Изменение привязки задним числом.** Прошлые факты останутся с прежней Массой — переписывать историю нельзя (правило «история не правится»). Значит, отчёт «Потребление материалов» за старый период покажет Массу, которой уже нет в привязке. Это нормально и должно быть записано в правилах, иначе это будут искать как дефект.

**R6. Обязательность расхода.** Если Масса у ГП теперь «одна», остаётся вопрос: можно ли внести факт с нулевым расходом Массы (фасовка из уже списанного ПФ, пересорт). Жёсткая обязательность сломает такие смены; свободная — вернёт «необязательный выбор», который владелец как раз убирает.

**R7. Права и аудит.** Экран привязок = инструмент, меняющий мастер-данные. Нужно право (например `nsi:manage` или отдельное `product:mass_binding`), запись в аудит и запрет молчаливой массовой правки. Без этого «сводная с корректировкой» станет способом тихо изменить номенклатуру.

**R8. Миграция и релиз.** Добавление полей/таблицы — миграция в `main`; начальное заполнение (21 ГП из истории) — разовый скрипт. Релиз не должен останавливать ввод фактов, пока привязки пусты — это требование к порядку работ, а не пожелание.

**R9. Сценарий приёмки усложняется.** Проверять придётся не «работает ли экран», а путь: планирование ГП только на разрешённых РЦ → факт с предзаполненной Массой → попытка вписать чужую Массу (отказ) → РЦ 13 с остатком ПФ и без → закрытие НП. Это сквозной сценарий, а не чек-лист (§14 правил).

## 5. Варианты внедрения

**A. Строгое правило сразу.** Привязка обязательна для планирования и ввода факта. *Плюс:* правило сразу честное. *Минус:* пока привязки нет, встанет планирование 176 ГП — требует заполнения всех привязок до релиза, то есть полной ручной или импортной работы на 176 позиций.

**B. Мягкий переход (рекомендую).** Правило действует для ГП с привязкой; для остальных поведение прежнее, но в интерфейсе видно «привязка не задана», а у НП/АДМ есть рабочий список. Строгий режим включается флагом/датой, когда список пуст. *Плюс:* производство не встаёт, данные приходят постепенно, риск нарастает управляемо. *Минус:* какое-то время в системе два поведения — это надо явно подписывать.

**C. Привязка из 1С.** Спецификация ведётся в 1С, мы принимаем её импортом. *Плюс:* один источник правды, 176 позиций не вводятся руками. *Минус:* это отдельная интеграционная задача (канал, формат, расписание), и пока её нет — ничего не работает.

Практичный порядок: **B сейчас + C отдельным решением**, с экраном из п.2 требования как обязательной частью (сводная для НП/АДМ нужна в любом варианте).

## 6. Файл 1С «спецификации» (`4-bom.xlsx`) — разобран, подходит

Владелец прислал выгрузку полной спецификации из 1С. Разобрана 19.11.2026.

**Формат:** один лист, 3902 строки, столбцы `Материал | Номенклатура | Доля | Категория | Код | Код материала`.

100 мл → 0.088, 5 л → 4.7 (проверено по объёму в наименовании ГП).

**Что из файла нужно нам** (решение владельца): из блока `Продукция` — только компоненты
**Масса** и **Туба**. Упаковка (бутылка, крышка, этикетка, гофроящик) и блоки `Масса`/`Сырьё`
не берутся.

## 7. Загрузчик (сделан, шаг записи ждёт схемы)

Код: `apps/web/src/lib/bom-import/` (чтение, разбор, план) и `apps/web/scripts/bom-plan.ts` (CLI).
Документация — `apps/web/scripts/README.md`.

**Как работает «обновляемый источник правды»:** файл из 1С → разбор → сверка с номенклатурой →
план (что привяжется, что пропущено и почему) → запись. Сейчас реализованы первые три шага
и выгрузка обработанного набора в CSV; запись не делается, потому что в схеме ещё нет поля
привязки — это часть решения по функции (см. §8).

Две вещи, которые выяснились только на реальном файле и уже закрыты:

1. **exceljs не читает выгрузку 1С.** Наш импорт номенклатуры (`lib/nsi-import/xlsx.ts`) работает
   на exceljs, а он падает на этом файле: «Cannot read properties of undefined (reading 'anchors')»
   — из-за графики и комментариев в архиве. Написан свой читатель `.xlsx` (ZIP + XML, без
   зависимостей, `lib/bom-import/xlsx.ts`).
2. **Кириллица и `\b`.** Первая версия разбора находила 261 Массу вместо 471: в JavaScript
   `\b` считает словом только латиницу, поэтому `^Масса\b` не совпадало ни с одной русской
   строкой. Плюс «Туба_М …» — рабочее имя тубы в 1С, подчёркивание тоже пришлось учесть (терялось
   15 привязок). Оба случая закрыты тестами.

**Что загрузчик гарантирует:** чужая структура файла не принимается молча (проверка заголовка);
вторая Масса у ГП не выбирается наугад, а попадает в отчёт; нулевая доля не превращается
в привязку без нормы; привязки, которых нет в файле, **не удаляются**, а попадают в рабочий
список «ГП без привязки».

## 8. Решения владельца (19.11.2026)

1. **Одна Масса на ГП.** Строка Массы в факте предзаполняется нормой из BOM × план; количество можно обнулить (фасовка из ранее списанного ПФ, пересорт).
2. **Отклонение от привязки запрещено** в обычном вводе; исключение — только через «Ввод за Оператора» с обязательной причиной и записью в аудит.
3. **Список РЦ фасовки** ведётся в ProdTrack на экране привязок. Пустой список = все фасовочные РЦ (поведение как сейчас). Предзаполнение — из истории (23 ГП уже выпускались, 6 из них на двух РЦ).
4. **13 ГП, которых нет в файле** — запрашивается новая выгрузка из 1С (дешевле и надёжнее ручного ввода).
5. **Расхождение `00-00004753`** — верить BOM, историю не трогать.
6. **258 ГП и 80 Масс из файла, которых нет в номенклатуре ProdTrack — вручную.** Возможно, часть позиций устарела и её нужно деактивировать, поэтому автозагрузка номенклатуры из файла запрещена: решение по каждой позиции принимает человек.
7. **Тубу привязываем сразу** (104 ГП), чтобы не переделывать: на следующем этапе появится параллельное производство и взаимодействие производственных складов. Сейчас — только привязка и хранение нормы, без правил расхода Тубы: пока Туба не производится, её расход никто не вводит.

Порядок безопасный: пока привязки не заполнены, правило не блокирует планирование — пустая привязка
означает «как раньше» (любая Масса), и такие ГП видны в рабочем списке.
