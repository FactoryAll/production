## Правила разработки

1. **Спеки — источник истины.** Код строго соответствует `specs/`. Любое отклонение — «предложение изменения спека», применяется только после согласования.
2. **DoD задачи:** код по спеку (BR/UC); unit-тесты на затронутые BR; миграция (если есть) применяется на пустой БД; нет N+1 и лишних запросов; UI на токенах `packages/ui`; коммит ссылается на задачу и BR.
3. **Перед каждым коммитом:** `pnpm typecheck && pnpm lint && pnpm test && pnpm build` — все exit 0. Красное не коммитить.
4. **Версионирование (ПРОЦ-02):** Фаза 6 — **major**, релиз `v2.0.0`. Версия в футере берётся из `docker-compose.yml` (build arg `VERSION`) — при выпуске поднять там и в `.env.example`.
5. **Доставка:** короткие коммиты в `main` + `git push`. Стейджить **явными путями** (`git add -- <файлы>`), а не `git add -A`: в рабочем дереве может работать параллельная сессия.
6. **Локальная БД недоступна** (peer-auth, нет sudo): проверяются unit-тесты, typecheck, build и офлайн-проверки схемы; миграции и сид выполняются на VPS.
7. **Ручное тестирование выполняет пользователь.** Агент готовит план, задания и фиксирует результаты.

## Уроки Фазы 5 (не повторять)

1. **Готовность данных важнее факта события.** Задача «Перемещение» для С1С появлялась при отправке, хотя количество ещё не подтвердила принимающая сторона. Событие в каталоге ≠ готовность данных: проверять состояние источника, а не сам факт перехода.
2. **«Поле не передано» ≠ «поле пустое».** Обёртка серверного действия не читала потребление из формы, а сервис трактовал отсутствие как «данных нет» — строки факта удалялись, движение по остатку терялось. Частичная правка не должна молча стирать непереданные поля.
3. **Сквозной путь формы проверяется отдельно.** Разбор `FormData` выносить в чистый модуль и покрывать тестом: ошибка в обёртке не видна ни типам, ни сервисным тестам.
4. **Автоматические поля ORM врут о смысле.** `@updatedAt` обновлялся при любой записи, включая отметку «обработано»; если колонка означает «изменение данных источника», время должен проставлять код.
5. **Ничего синхронного из `'use server'`.** Урок Фазы 4 повторился: экспорт хелпера из файла серверных действий ломает `next build` (видно только на сборке).
6. **Схему можно менять без миграции**, если DDL не меняется (замена `@updatedAt` на обычное поле): миграция нужна только при изменении структуры БД.
7. **Каждое исправление — с тестом, который падал бы без него**, и перепроверкой на развёрнутой версии (найденный при перепроверке регресс T-073 — ровно об этом).
8. **Удаление системных записей при «неготовности» источника** — рабочий приём: правило поменялось, старые записи самоисправляются на ближайшем переходе.
9. **Даты в документах сверять** с серверным временем и записями БД: в отчётах Фазы 5 была опечатка на день.
10. **Данные, испорченные дефектом, восстанавливать явно** и фиксировать это в отчёте (состав потребления факта возвращали SQL-вставкой на VPS).

## Правила коммуникации

- Язык — **русский**.
- **Формат работы (строго, `process.md` §4.2.1):** агент выдаёт **ровно одно задание** (действие → ожидаемый результат → что прислать) и **ждёт ответ**. Никаких списков задач «на будущее» и «заодно проверьте» в одном сообщении. Результат ОК — следующее задание; не ОК — сначала разбираемся с текущим.
- **Команды для VPS** — один блок на одно задание; пользователь выполняет и возвращает вывод. Агент не имеет доступа к серверу.
- **Дефекты:** критичные (блокируют работу или искажают данные) — исправляем немедленно; некритичные — сразу после обнаружения, с пометкой в отчёте о тестировании.
- **Отчёты** — по форматам `process.md` §6: для Фазы 6 — `docs/phase_6_selfcheck_report.md`, `docs/release_v2.0.0_report.md`, `docs/release_v2.0.0_test_plan.md`, `docs/release_v2.0.0_test_report.md`.
- Перед утверждением о содержимом файла — **прочитать файл**. При неясности — задать вопрос, не догадываться.

## Редеплой на VPS (проверенная процедура)

```bash
cd /opt/prodtrack
git fetch origin && git pull origin main
git log -1 --oneline
docker compose down
docker compose build --no-cache
docker compose up -d
sleep 25
bash scripts/postdeploy-check.sh
```

Особенности (проверено на практике):

1. Версия в футере встраивается **на этапе сборки** (`next.config.js` → `env.VERSION`), поэтому после подъёма версии нужен `build --no-cache`.
2. Миграции и сид в контейнере запускаются **не** через `pnpm --filter`:
   ```bash
   docker compose exec -T web sh -lc 'prisma migrate deploy --schema=/app/packages/db/prisma/schema.prisma'
   docker compose exec -T web sh -lc 'cd /app/packages/db && tsx prisma/seed.ts'
   ```
3. `docker compose down` удаляет логи: при разборе ошибки снять `docker compose logs --tail=50 web` **до** перезапуска.
4. Сервер общий (соседи: `mes-midex.factoryall.ru`, `tracker.factoryall.ru`) — ничего лишнего не трогать, после деплоя проверять их доступность. Известно: `tracker` не запущен на хосте (nginx проксирует его на порт 8000), к ProdTrack не относится.
