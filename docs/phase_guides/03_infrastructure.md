# Как создаётся инфраструктура: состав работ этапа и передача в проверку

> Этап 3 сквозного процесса (`00_workflow_overview.md`). Универсальный документ: опирается на практику одного пройденного
> этапа создания инфраструктуры. Специфика модулей, продуктов и значений сюда не входит — документ переносим
> в другие аналогичные проекты.
> Источник: отчёт чата разработки инфраструктуры. Проверка инфраструктуры на развёрнутом контуре в этой практике
> велась вне чата создания, поэтому она отражена только там, где о ней есть факты (см. §8 и §12).

---

## 1. Назначение и место этапа в общем процессе

Этап 3 каркаса: **создание инфраструктуры**, на которой далее выполняются фазы. Вход этапа — список задач с зависимостями,
приоритетами и критериями приёмки, спецификации (обзорный документ, модульные спеки, документ технических решений)
и ранее созданные артефакты: инициализированный репозиторий с соглашениями о коммитах и заготовки документов.
Выход — рабочая площадка, слой данных, каркас аутентификации, пакет контрактов, ядро сквозной записи
и конвейер непрерывной интеграции как код.

Чем этап отличается от соседних:

| Признак | Этап 2 (спеки) | Этап 3 (инфраструктура) | Этап 4 и далее (фазы) |
|---------|----------------|--------------------------|------------------------|
| Предмет работы | требования и их согласованность | площадка, на которой всё будет работать | функциональность по спекам |
| Единица работы | документ и правило | задача инфраструктуры с веткой на задачу | задача фазы |
| Что считается прогрессом | закрытое решение, отражённое во всех документах | работающий фундамент и зелёный пайплайн качества | работающая и принятая функциональность |
| Чем завершается | стартовым промптом следующего этапа | стартовым промптом следующего этапа | стартовым промптом следующего этапа или фазы |
| Проверка | согласованность набора | локальные проверки и передача контура на независимую проверку | приёмка фазы по правилам проекта |

**Ключевая особенность этапа.** Он создаёт **фундамент, от которого зависят все последующие фазы**: сквозные записи
(событие, аудит, хронометраж) делаются один раз здесь, а задачи последующих фаз работают поверх них в режиме чтения.
Поэтому перестройка зависимостей на этом этапе — нормальная часть работы, а не отклонение.

## 2. Границы этапа

| Относилось к этапу | Явно вне этапа |
|--------------------|----------------|
| Развёртывание рабочей площадки: структура хранилища кода с разделением на части (приложение, слой данных, контракты, интерфейсные компоненты, общие конфигурации), единые правила качества | Независимая проверка инфраструктуры: развёртывание контура, применение миграций к живой базе, идемпотентность на реальных данных, поведение за обратным прокси, браузерные сквозные сценарии, сборка контейнерного образа |
| Слой данных: схема, базовая миграция, генерация типизированного клиента, идемпотентное наполнение справочников | Наполнение содержательных модулей и бизнес-логика фаз |
| Библиотека дизайн-токенов и базовых компонентов интерфейса | Приёмка фаз и релизный процесс (правила проекта и документ этапа 4) |
| Каркас аутентификации: модель сессии, cookie, проверка на входе | Содержательные требования — они приходят из спек; здесь только их инфраструктурная часть |
| Пакет контрактов (перечисления, константы, проверки типов, общие для сервера и клиента) | — |
| Ядро сквозной записи (события, аудит, хронометраж) | — |
| Конвейер непрерывной интеграции как код | Прогон конвейера на стороне удалённой системы |

**Важное разграничение.** Локальный прогон пайплайна качества перед коммитами — это порядок разработки внутри этапа,
а не проверка инфраструктуры. Проверка контура выполняется владельцем на развёрнутой версии.

## 3. Состав работ этапа

| Шаг | Что делается | Зачем |
|-----|--------------|-------|
| 1. Рабочая площадка | Хранилище с разделением на части: приложение, слой данных, пакет контрактов, пакет интерфейсных компонентов, общий пакет конфигураций компилятора | Единая точка сборки и общие настройки: дальше всё создаётся внутри неё |
| 2. Единые правила качества | Общая конфигурация линтера и форматирования, единый стиль кода для всех частей | Соглашения фиксируются в репозитории, а не в переписке |
| 3. Конвейер непрерывной интеграции | Две стадии: проверка изменений (линтер, типы, модульные тесты, сборка) и основная ветка (дополнительно браузерные сквозные проверки и сборка контейнерного образа) | Автоматизация повторяющегося шага вместо ручной проверки |
| 4. Слой данных | Схема данных по всем сущностям спецификаций, базовая миграция, генерация типизированного клиента | Единый источник структуры данных для сервера, миграций и типов |
| 5. Наполнение справочников | Идемпотентный скрипт наполнения: справочники, склады, смены, причины | Повторный запуск не должен дублировать записи |
| 6. Дизайн-токены | Набор переменных оформления (цвета, шкала нейтральных, типографика, радиусы, границы, высоты элементов) и конфигурация темы | Единая визуальная основа для всех экранов |
| 7. Базовые компоненты интерфейса | Кнопка, карточка, поле ввода, диалог, таблица; компоненты опираются на токены | Прикладные экраны собираются из библиотеки, а не из разрозненных элементов |
| 8. Каркас аутентификации | Модель сессии с ограниченным сроком, cookie только для сервера, проверка сессии на входе с перенаправлением на страницу входа, экран входа и экран смены пароля | Защита закрытых маршрутов до появления содержательных модулей |
| 9. Пакет контрактов | Перечисления, константы и проверки-охранники типов, разделяемые сервером и клиентом; пакет намеренно не зависит от слоя данных | Исключить рассинхрон значений между сервером и клиентом |
| 10. Ядро сквозной записи | Функции записи — событие, аудит, хронометраж — принимающие клиент транзакции и выполняющие только добавление | Сквозные записи делаются в той же транзакции, что и бизнес-изменение, и не дублируются по модулям |
| 11. Тесты частей | Модульные тесты на контракты, компоненты и ядро записи | Каждая задача проходит по своему определению готовности |

## 4. Порядок и зависимости

**Обязательные условия (фундамент → всё остальное):**

1. Рабочая площадка и общие конфигурации — без них не собирается ни одна часть.
2. Конвейер непрерывной интеграции — после площадки и до остальных задач: дальнейшие коммиты проверяются им.
3. Схема данных — условие для наполнения справочников и для каркаса аутентификации.
4. Токены оформления — условие для базовых компонентов интерфейса.
5. Контракты — условие для ядра сквозной записи.
6. Ядро сквозной записи — условие для сквозных задач последующих фаз.

**Что шло параллельно:** слой данных и пакет контрактов — независимые направления; токены и компоненты интерфейса —
независимо от слоя данных.

**Перестройка зависимостей по решению владельца.** Сквозные задачи последующих фаз (генерация событий, хронометраж,
аудит) переведены в режим **чтения поверх ядра записи**: запись выполняет ядро, чтобы не появилось двух источников
одних и тех же записей. Задача ядра добавлена в нулевую фазу и включена в перечень зависимостей этих задач.

**Наблюдение о параллелизме.** Одновременная работа нескольких исполнителей в одном рабочем каталоге над разными
задачами приводила к конфликтам файлов и веток. После этого оставшиеся задачи выполнялись последовательно,
по одной ветке на задачу.

## 5. Решения владельца и способ их фиксации

| Решение | Как зафиксировано |
|---------|-------------------|
| Добавить сквозную задачу ядра записи в нулевую фазу | Запись в списке задач; включение в зависимости сквозных задач |
| Сквозные задачи читают поверх ядра, а не пишут повторно | Формулировки задач переписаны явно («не дублирует запись») |
| Разделить близкие по смыслу категории на независимые перечисления с разным составом значений | Записи в списке задач и в документе технических решений |
| Каждая задача — отдельная ветка с последующим слиянием в основную | Формат истории репозитория; слияние только быстрым перемещением указателя |
| Состав нулевой фазы — обязательный минимум; следующая фаза не начинается без явной приёмки | Отчёт по завершении фазы и остановка работ |
| Формат отчёта о завершении: закрытые задачи, результат конвейера, идемпотентность наполнения, открытые вопросы | Текст отчёта |

Отдельного протокола решений не велось: решение, прозвучавшее в переписке, переносилось в артефакт репозитория
(список задач, документ технических решений, ветки и коммиты), и **носителем решения становился сам артефакт**.

## 6. Артефакты этапа

| Артефакт | Где живёт |
|----------|-----------|
| Хранилище с разделением на части (приложение, данные, контракты, интерфейсные компоненты, общие конфигурации) | корень репозитория |
| Конфигурация линтера и форматирования, правила игнорирования | корень репозитория |
| Конвейер непрерывной интеграции (две стадии) | каталог конфигурации конвейера |
| Схема данных и базовая миграция | часть «данные» |
| Скрипт идемпотентного наполнения справочников | часть «данные» |
| Типизированный клиент доступа к данным | генерируется из схемы |
| Набор дизайн-токенов | часть «интерфейсные компоненты» |
| Базовые компоненты интерфейса | часть «интерфейсные компоненты» |
| Контракты: перечисления, константы, проверки типов | часть «контракты» |
| Ядро сквозной записи (событие, аудит, хронометраж) | часть «данные» |
| Модель сессии, проверка на входе, экраны входа и смены пароля | приложение |
| Модульные тесты частей | рядом с кодом соответствующих частей |
| Обновлённые список задач и документ технических решений | каталог документации проекта |
| Ветки задач и коммиты в основной ветке | система контроля версий |

**Чего на этом этапе не появилось:** конфигурация развёртывания контура (обратный прокси, сертификаты, планировщик,
мониторинг, хранилище) — **[требуется уточнение]**: относится ли она к этому этапу или к отдельному.

## 7. Критерии готовности к передаче в проверку

Инфраструктура считалась готовой к проверке при одновременном выполнении:

1. **Все обязательные задачи этапа закрыты** — по одной ветке на задачу, все ветки слиты в основную.
2. **Пайплайн качества на итоговом состоянии основной ветки зелёный**: сборка, линтер, проверка типов, модульные тесты.
3. **Конвейер непрерывной интеграции существует как код** и различает проверку изменений и проверку основной ветки.
4. **Базовая миграция зафиксирована**, генерация типизированного клиента проходит.
5. **Наполнение справочников идемпотентно по построению** (см. §10).
6. **Непроверяемое локально вынесено явно**: всё, что требует живой базы данных и развёрнутого контура, перечислено
   как непроверенное и передаётся на независимую проверку.
7. **Явная приёмка владельца** — без неё следующая фаза не начинается.
8. **Стартовый промпт следующего этапа подготовлен** — обязательный артефакт завершения (каркас §4): документ,
   который целиком переносится в новый чат и передаёт состояние инфраструктуры, источники истины, правила, уроки
   и первый шаг следующего этапа.

## 8. Что проверялось внутри этапа, а что нет

| Проверялось на этапе | Проверялось вне этапа |
|----------------------|----------------------|
| Пайплайн качества: сборка, линтер, проверка типов, модульные тесты | Применение миграций к живой базе целевого контура |
| Базовая миграция как артефакт (зафиксирована, генерация клиента проходит) | Идемпотентность наполнения на реальных данных |
| Идемпотентность наполнения по построению (см. §10) | Поведение за обратным прокси, внешняя доступность, сертификаты |
| Модульные тесты контрактов, компонентов и ядра записи | Браузерные сквозные сценарии, сборка контейнерного образа, восстановление после перезапуска |

На этапе действовало правило: **что не проверено — то названо непроверенным**. Список того, что требует живой среды,
передавался дальше вместе с результатом. Состав проверки контура в практике этого этапа не описан —
**[требуется уточнение]**: чем подтверждалась работа инфраструктуры на развёрнутой версии.

## 9. Роли и формат взаимодействия

| Роль | Что делает на этапе |
|------|---------------------|
| **Агент** | Разбирает спецификации и список задач, предлагает план, создаёт артефакты по одной задаче на ветку, правит зависимости задач, вносит изменения в список задач и документ технических решений, готовит отчёт о завершении этапа |
| **Владелец продукта** | Задаёт правки к составу задач, определяет формат веток и слияния, принимает решения по составу и разделению сущностей, требует отчёт и явную приёмку перед следующей фазой |

Формат: одно задание на сообщение; отчёт агента — короткий и предметный; списки задач «на будущее» не выдавались.

## 10. Уроки и грабли этапа

| Что произошло | Как исправлялось | Правило на будущее |
|---------------|------------------|--------------------|
| Несколько исполнителей работали в одном рабочем каталоге над разными задачами: файлы одной задачи попадали в дерево другой, ветки создавались от неверного состояния | Работа остановлена, оставшиеся задачи выполнены последовательно, по одной ветке на задачу | Одна задача — один исполнитель и одна ветка; параллелизм требует изоляции рабочих копий |
| Коммит попал в основную ветку вместо ветки задачи: создание ветки завершилось ошибкой (имя уже существовало), код возврата не проверялся | Коммит перенесён на ветку задачи, основная ветка возвращена назад, слияние выполнено повторно | Перед коммитом проверяются текущая ветка и код возврата предыдущей команды; создание ветки — проверяемая операция |
| В область компиляции одной из частей попадал каталог со скриптом наполнения: сборка падала на файле вне корня исходников, рядом появлялись сгенерированные артефакты | Область компиляции ограничена исходниками; сгенерированные артефакты внесены в правила игнорирования | Область компиляции и правила игнорирования определяются вместе с частью, а не после первой ошибки |
| Клиент доступа к данным был импортирован в точку входа, исполняемую в ограниченной среде: сборка не прошла | Проверка на входе оставлена как проверка наличия cookie; обращение к данным перенесено на серверную сторону | Точки входа с ограниченной средой исполнения не должны тянуть за собой клиент базы данных |
| Набор токенов оформления подключался отдельным файлом со слоем, а базовое правило слоёв отсутствовало: сборка стилей падала | Определения токенов размещены так, чтобы базовое правило предшествовало слоям | Порядок подключения слоёв фиксируется в точке интеграции, а не предполагается |
| Конфигурация темы существовала в двух местах, приложение ссылалось на удалённую копию: сборка падала | Оставлен один источник конфигурации темы | У каждого файла конфигурации один владелец |
| Правка контрактов считалась выполненной по отчёту исполнителя, но проверок типов и тестов не было | Проверено по артефакту, добавлена отдельная ветка с проверками и тестами | Считается сделанным то, что видно в артефакте, а не то, что заявлено в отчёте |
| Наполнение справочников требовалось сделать повторно запускаемым, но не у всех сущностей есть естественный уникальный ключ | Для сущностей с ключом — обновление-или-вставка по ключу; для остальных — поиск существующей записи перед вставкой | Идемпотентность требует естественного уникального ключа; где его нет — явный поиск перед записью |

**Что сработало и стоит сохранить.** Сквозная запись оформлена функциями, принимающими клиент транзакции, — это
единственный способ гарантировать, что событие, аудит и хронометраж попадают в ту же транзакцию, что и бизнес-изменение,
и не дублируются по модулям. Задачи последующих фаз работают поверх этого ядра только на чтение.

## 11. Пробелы: что требует уточнения

1. **Доступ к живой базе данных в среде разработки** — отсутствовал; применение миграций и наполнение на реальной
   базе в чате создания не выполнялись. **[требуется уточнение]** — как в проекте предоставляется такой доступ.
2. **Конфигурация развёртывания контура** (обратный прокси, сертификаты, планировщик, мониторинг, хранилище) —

## 12. Краткий чек-лист этапа

**Площадка:** хранилище с разделением на части создано → общие конфигурации компилятора на месте → правила качества
и правила игнорирования зафиксированы в репозитории → конвейер непрерывной интеграции существует как код и различает
проверку изменений и проверку основной ветки.

**Данные:** схема по всем сущностям спецификаций → базовая миграция → генерация типизированного клиента проходит →
наполнение справочников идемпотентно (ключ или явный поиск перед вставкой).

**Каркас:** токены оформления в одном источнике → базовые компоненты опираются на токены → модель сессии и проверка
на входе закрывают маршруты → контракты не зависят от слоя данных → ядро сквозной записи принимает клиент транзакции.

**Порядок:** одна задача — один исполнитель и одна ветка → зависимости пересобраны, если сквозные задачи переведены
в режим чтения → слияние в основную ветку только быстрым перемещением указателя.

**Передача:** пайплайн качества зелёный → миграция и генерация клиента проходят → непроверяемое локально перечислено
явно → отчёт о завершении подготовлен → приёмка владельца получена → подготовлен **стартовый промпт следующего
этапа** (обязательный артефакт завершения, каркас §4) → только после этого начинается следующая фаза.
