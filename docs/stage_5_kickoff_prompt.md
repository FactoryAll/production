## Правила работы

1. **Спеки — источник истины.** Код строго соответствует `specs/`. Любое отклонение — «предложение изменения спека»,
   применяется только после согласования. Расхождения собираются письменно (см. §5 отчёта самопроверки фазы 6 как образец).
2. **Перед каждым коммитом:** `pnpm typecheck && pnpm lint && pnpm test && pnpm build` — все exit 0. Красное не коммитить.
3. **Доставка:** короткие коммиты в `main` + `git push`. Стейджить **явными путями** (`git add -- <файлы>`),
   а не `git add -A`: в рабочем дереве может работать параллельная сессия.
4. **Дефекты:** критичные (блокируют работу или искажают данные) — исправляем немедленно; некритичные — сразу после
   обнаружения. Каждое исправление — с тестом, который **падал бы без него**, и с перепроверкой на развёрнутой версии.
5. **Что проверяется локально, а что нет:** локально — типы, линтер, тесты, сборка, e2e, миграции и сид на локальной БД;
   на сервере — только то, что требует живой сессии, реальных данных и прокси. Непроверенное указывается прямо.
6. **Ручное тестирование выполняет пользователь.** Агент готовит план, задания и фиксирует результаты.

## Локальная среда (проверено в фазе 6)

- **PostgreSQL локально доступен:** развёрнут собственный кластер 16 (данные в `/tmp/pgdata`, порт 55432, доверительная
  аутентификация). Это позволяет проверять `prisma migrate deploy` на пустой базе и идемпотентность `db:seed` ×2
  без VPS. Если кластер не поднят — `initdb` + `pg_ctl` из `/usr/lib/postgresql/16/bin`.
- **E2E гоняется локально:** `PW_CHROMIUM_PATH=$HOME/.cache/ms-playwright/chromium-1217/chrome-linux64/chrome`,
  в `DATABASE_URL` полезно добавлять `&connection_limit=5` (иначе параллельные воркеры Playwright исчерпывают
  соединения: пул Prisma = 2×CPU+1).
- **Не запускать e2e и `pnpm build` одновременно** — оба пишут в `apps/web/.next` и сборка падает.
- **CI:** `.github/workflows/main.yml` (push в `main`: качество + e2e + docker) и `pr.yml` (pull request: качество + e2e).
  E2E-джоб добавлен в фазе 6 — до этого он запускался только после мержа, и поломка контура копилась незаметно.

## Уроки этапа 4 (что нельзя повторять)

1. **Область видимости по умолчанию — закрытая.** Если у роли ограниченный доступ, отсутствие данных для ограничения
   (например, учётная запись Оператора не привязана к сотруднику) должно давать **пустой результат**, а не «без фильтра».
   В фазе 6 непривязанный Оператор видел данные всего предприятия — это критичный дефект.
2. **Не показывать то, что роль не вправе открыть.** Ссылки на документы, недоступные роли, ведут на экран
   «Доступ запрещён». Список документов должен строиться с учётом прав, а не только ролей.
3. **Состояние формы в постоянно смонтированном диалоге не сбрасывается.** Диалоги НСИ жили всё время работы экрана,
   и при «Редактировать» поля оставались пустыми — дефект с M01, найденный только в фазе 6. Лечится ключом по
   идентификатору записи; проверяется тестом, который монтирует **страницу**, а не компонент диалога.
4. **Проверять тестом, который падает без исправления.** Иначе тест подтверждает сам себя.
5. **Числа и подписи — часть интерфейса.** Согласование числа с существительным («2 перемещения», а не «2 перемещений»),
   формат длительности для значений свыше суток («42 д 00:00», а не «1006:59»).
6. **Модель данных влияет на трактовку спеки.** Справочник смен — две шаблонные строки с датой-заглушкой, поэтому
   «ПЗ текущей смены» (BR-5) пришлось трактовать по номеру смены и времени суток; корневое решение — задача T-075.
7. **Часовой пояс.** Приложение и тесты должны работать в одном поясе: смена и «текущая смена» зависят от локального
   времени (Р-05). E2E-сценарий, который брал смену №1 независимо от часов, падал в CI (UTC) и проходил локально (MSK).
8. **Проверять код возврата пайплайна ДО коммита.** Один коммит в фазе 6 ушёл с красным `tsc`: тестовая фикстура
   не проходила типы, но `vitest` типы не проверяет, поэтому локально тест «проходил». CI по коммиту упал.
9. **Веб-тесты видят собранный `dist` рабочих пакетов.** Изменения в `packages/db` не влияют на тесты
   приложения, пока пакет не пересобран: «зелёные» тесты могут проверять старый код. Полный пайплайн пересобирает пакеты сам.
10. **Разрушительный инструмент проверяется на живой базе, а не только юнит-тестами.** Очистка данных (T-076) и скрипт-бэкфилл
   смен (T-075) прогонялись на реальной базе: там и выясняется, что каскады и порядок удаления выбраны верно.
11. **Смена — это данные, а не справочник.** В форме ПЗ выбираются дата и номер смены (1-я / 2-я), запись создаёт система;
   экран НСИ «Смены» — только просмотр. Не возвращайте ручное ведение смен.
8. **Агент изображения не читает.** Подтверждения принимаются **текстом**: копия содержимого экрана, вывод команд, значения полей.
9. **Восстановление данных после теста — часть шага.** Если проверка меняет рабочие данные, в задании отдельным пунктом
   указывается возврат к исходному состоянию (так проверялась корректировка потребления: 259 → 258 → 259).

## Редеплой на VPS (проверенная процедура)

```bash
cd /opt/prodtrack
git fetch origin && git pull origin main
git log -1 --oneline
docker compose down
docker compose build --no-cache
docker compose up -d
sleep 25
bash scripts/postdeploy-check.sh
```

Особенности (проверено на практике):

1. Версия в футере встраивается **на этапе сборки** (`next.config.js` → `env.VERSION`), поэтому после
   подъёма версии нужен `build --no-cache`.
2. Миграции и сид в контейнере запускаются **не** через `pnpm --filter`:
   ```bash
   docker compose exec -T web sh -lc 'prisma migrate deploy --schema=/app/packages/db/prisma/schema.prisma'
   docker compose exec -T web sh -lc 'cd /app/packages/db && tsx prisma/seed.ts'
   ```
3. `docker compose down` удаляет логи: при разборе ошибки снять `docker compose logs --tail=50 web` **до** перезапуска.
4. Сервер общий (соседи: `mes-midex.factoryall.ru`, `tracker.factoryall.ru`) — ничего лишнего не трогать,
   после деплоя проверять их доступность. Известно: `tracker` не запущен на хосте (nginx проксирует его на порт 8000),
   к ProdTrack не относится.
