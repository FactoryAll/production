## Правила работы

1. **Спеки — источник истины.** Код строго соответствует `specs/`. Любое отклонение — «предложение изменения спека»,
   применяется только после согласования. Расхождения собираются письменно (см. §5 отчёта самопроверки фазы 6 как образец).
2. **Перед каждым коммитом:** `pnpm typecheck && pnpm lint && pnpm test && pnpm build` — все exit 0. Красное не коммитить.
3. **Доставка:** короткие коммиты в `main` + `git push`. Стейджить **явными путями** (`git add -- <файлы>`),
   а не `git add -A`: в рабочем дереве может работать параллельная сессия.
4. **Дефекты:** критичные (блокируют работу или искажают данные) — исправляем немедленно; некритичные — сразу после
   обнаружения. Каждое исправление — с тестом, который **падал бы без него**, и с перепроверкой на развёрнутой версии.
5. **Что проверяется локально, а что нет:** локально — типы, линтер, тесты, сборка, e2e, миграции и сид на локальной БД;
   на сервере — только то, что требует живой сессии, реальных данных и прокси. Непроверенное указывается прямо.
6. **Проверку на живых данных выполняют пользователи.** В ОПЭ владелец собирает обратную связь и формулирует задания;
   агент выполняет их, готовит задания на перепроверку, фиксирует результаты и ведёт журнал ОПЭ.

## Уроки этапа 4 (что нельзя повторять)

1. **Область видимости по умолчанию — закрытая.** Если у роли ограниченный доступ, отсутствие данных для ограничения
   (например, учётная запись Оператора не привязана к сотруднику) должно давать **пустой результат**, а не «без фильтра».
   В фазе 6 непривязанный Оператор видел данные всего предприятия — это критичный дефект.
2. **Не показывать то, что роль не вправе открыть.** Ссылки на документы, недоступные роли, ведут на экран
   «Доступ запрещён». Список документов должен строиться с учётом прав, а не только ролей.
3. **Состояние формы в постоянно смонтированном диалоге не сбрасывается.** Диалоги НСИ жили всё время работы экрана,
   и при «Редактировать» поля оставались пустыми — дефект с M01, найденный только в фазе 6. Лечится ключом по
   идентификатору записи; проверяется тестом, который монтирует **страницу**, а не компонент диалога.
4. **Проверять тестом, который падает без исправления.** Иначе тест подтверждает сам себя.
5. **Числа и подписи — часть интерфейса.** Согласование числа с существительным («2 перемещения», а не «2 перемещений»),
   формат длительности для значений свыше суток («42 д 00:00», а не «1006:59»).
6. **Модель данных влияет на трактовку спеки.** Справочник смен был двумя шаблонными строками с датой-заглушкой,
   поэтому «ПЗ текущей смены» (BR-5) пришлось сначала трактовать по номеру смены; в v2.1.0 смена стала данными (T-075),
   и правило считается по дате и номеру. Если видите странность в показателе — сначала проверьте модель данных.
7. **Часовой пояс.** Приложение и тесты должны работать в одном поясе: смена и «текущая смена» зависят от локального
   времени (Р-05). E2E-сценарий, который брал смену №1 независимо от часов, падал в CI (UTC) и проходил локально (MSK).
8. **Проверять код возврата пайплайна ДО коммита.** Один коммит в фазе 6 ушёл с красным `tsc`: тестовая фикстура
   не проходила типы, но `vitest` типы не проверяет, поэтому локально тест «проходил». CI по коммиту упал.
9. **Веб-тесты видят собранный `dist` рабочих пакетов.** Изменения в `packages/db` не влияют на тесты
   приложения, пока пакет не пересобран: «зелёные» тесты могут проверять старый код. Полный пайплайн пересобирает пакеты сам.
10. **Разрушительный инструмент проверяется на живой базе, а не только юнит-тестами.** Очистка данных (T-076) и
   скрипт-бэкфилл смен (T-075) прогонялись на реальной базе: именно там выясняется, что каскады и порядок удаления верны.
11. **Команды на сервере запускаются в контейнере — без `pnpm exec`.** В образ попадает только пакет `@prodtrack/db`, и
   `pnpm exec` пытается доустановить зависимости и падает. Проверенная форма — прямой вызов (`tsx prisma/seed.ts`),
   как в `scripts/postdeploy-check.sh`. Локально, при полном рабочем дереве, `pnpm exec` работает.
12. **Сид не должен возвращать то, что система удаляет или деактивирует.** Он поднимал шаблонные смены обратно в активные
   при каждом деплое, и деактивация бэкфиллом не держалась: дефект нашли только в ручном тестировании.
13. **Даты в документах сверять с сервером.** Работа шла несколько дней, и «сегодня» из прошлого сообщения уже неверно:
   перед каждым заданием с датой (смена, период, отчёт) сверяйтесь с временем сервера или записями журнала.
14. **Смена — это данные, а не справочник.** В форме ПЗ выбираются дата и номер смены (1-я / 2-я), запись создаёт система;
   экран НСИ «Смены» — только просмотр. План нельзя поставить на прошедшую смену: у поля даты есть минимум, и та же
   проверка стоит на сервере. Не возвращайте ручное ведение смен.
15. **Агент изображения не читает.** Подтверждения принимаются **текстом**: копия содержимого экрана, вывод команд, значения полей.
16. **Восстановление данных после теста — часть шага.** Если проверка меняет рабочие данные, в задании отдельным пунктом
   указывается возврат к исходному состоянию; перед финальным прогоном базу удобно почистить экраном «Данные».

## Состав работ этапа 5 (согласован владельцем 12.10.2026)

**Решение владельца:** этап проводится как **опытная эксплуатация (ОПЭ)**, а не как повторный сквозной прогон.
Все фазы 0–6 прошли ручное тестирование и приняты — повторять их сценарии незачем. Невыполненные пункты бэклога
признаны **неблокирующими**: этап из-за них не задерживается.

### Цикл этапа

1. **Владелец запускает приложение в ОПЭ** — прод `https://prodtracker.factoryall.ru`, версия `v2.1.0`;
   к работе допускаются реальные пользователи.
2. **Пользователи работают** на своих данных; владелец **снимает обратную связь** и формулирует из неё задания агенту —
   **по одному на сообщение**.
3. **Агент выполняет задание:** уточняет при необходимости, вносит исправление или доработку, покрывает тестом,
   который падает без правки, прогоняет пайплайн, доставляет в `main` и выдаёт владельцу задание на перепроверку.
4. **Пользователи перепроверяют** на развёрнутой версии — те, кто сообщил о проблеме; владелец фиксирует результат текстом.
5. **По ходу ОПЭ владелец даёт задания по модернизации** — приоритет его.

**Перед допуском пользователей:** операционные данные, оставшиеся от ручного тестирования, стоит убрать экраном
администратора «Данные» (T-076) — он чистит их по группам (остатки — по каждому складу отдельно), не трогая
справочники, пользователей, роли и журнал аудита (см. состояние данных в `docs/release_v2.1.0_test_report.md`).

### Что входит

- любые находки живой эксплуатации: дефекты, неудобства, неверные трактовки, пожелания;
- доработки и модернизация по заданиям владельца;
- эксплуатационные вопросы, если владелец их поставит (резервное копирование, cron архивации аудита, журналы контейнеров,
  поведение после перезапуска, соседи по серверу).

### Что НЕ входит

- повторный сквозной прогон сценариев M01–M13 и повторная проверка сквозных правил (Р-07, Р-19, Р-21/Р-22, Р-23, 00 §4.2) —
  всё это проверялось при приёмке фаз;
- регресс-чек-лист по дефектам v1.0.0…v2.1.0 — закрытые дефекты не перепроверяются; если поведение всплывёт снова,
  оно разбирается как новая находка;
- плановые нефункциональные замеры (N+1, пагинация, объёмы) — только по отдельному заданию владельца.

Самостоятельно объём не расширять: любое «заодно» — отдельное задание владельца.

### Находки и журнал

Каждая находка фиксируется в журнале ОПЭ `docs/pilot_operation_journal.md`: дата, источник, суть, категория
(дефект / доработка / вопрос), критичность, статус, где исправлено, кем перепроверено. Критичные дефекты исправляются
немедленно (при необходимости — patch-хотфикс), некритичные — сразу после обнаружения; находка закрывается только
после перепроверки на развёрнутой версии.

### Критерий завершения этапа

Этап закрывается **решением владельца** о том, что ОПЭ состоялась. К этому моменту:

1. журнал ОПЭ закрыт: по каждой находке есть решение (исправлено / отложено / отклонено), исправленные перепроверены;
2. открытых критичных дефектов нет;
3. поток новых находок иссяк;
4. результат записан в `docs/phase_guides/05_final_testing.md` (§11) и оформлен отчёт этапа `docs/final_testing_report.md`;
5. подготовлен стартовый промпт этапа 6 (каркас §4) — обязательный артефакт передачи контекста.

Отдельный релиз по итогам этапа — **по решению владельца**: исправления и так уходят в `main` и разворачиваются,
версия нужна только если захочется зафиксировать этап тегом.

## Формат взаимодействия

- Язык — **русский**.
- **Строго одно задание на сообщение** (`process.md` §4.2.1): действие → ожидаемый результат → что прислать.
  Никаких списков «на будущее» и «заодно проверьте»; результат ОК — следующее задание, не ОК — сначала разбираемся с текущим.
- **Команды для VPS** — один блок на одно задание; пользователь выполняет и возвращает вывод. Доступа к серверу у агента нет.
- **Подтверждения — текстом** (агент изображения не читает): копия содержимого экрана, вывод команд, значения полей.
- **Отчёты** — для этого этапа: документ этапа `docs/phase_guides/05_final_testing.md` (модель ОПЭ; результат
  дописывается в §11 при закрытии этапа), рабочий **журнал ОПЭ** `docs/pilot_operation_journal.md` (одна находка —
  одна строка) и итоговый отчёт этапа `docs/final_testing_report.md` (пишется при закрытии; образец —
  `docs/release_v2.0.0_test_report.md`). Отдельного «плана ручного тестирования» этап не имеет: его роль
  выполняют журнал ОПЭ и задания владельца.
- Перед утверждением о содержимом файла — **прочитать файл**. При неясности — задать вопрос, не догадываться.

## Редеплой на VPS (проверенная процедура)

```bash
cd /opt/prodtrack
git fetch origin && git pull origin main
git log -1 --oneline
docker compose down
docker compose build --no-cache
docker compose up -d
sleep 25
bash scripts/postdeploy-check.sh
```

Особенности (проверено на практике):

1. Версия в футере встраивается **на этапе сборки** (`next.config.js` → `env.VERSION`), поэтому после
   подъёма версии нужен `build --no-cache`.
2. Миграции и сид в контейнере запускаются **не** через `pnpm --filter`:
   ```bash
   docker compose exec -T web sh -lc 'prisma migrate deploy --schema=/app/packages/db/prisma/schema.prisma'
   docker compose exec -T web sh -lc 'cd /app/packages/db && tsx prisma/seed.ts'
   ```
3. `docker compose down` удаляет логи: при разборе ошибки снять `docker compose logs --tail=50 web` **до** перезапуска.
4. Сервер общий (соседи: `mes-midex.factoryall.ru`, `tracker.factoryall.ru`) — ничего лишнего не трогать,
   после деплоя проверять их доступность. Известно: `tracker` не запущен на хосте (nginx проксирует его на порт 8000),
   к ProdTrack не относится.
