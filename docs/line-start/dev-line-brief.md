# Брифинг рабочей линии ProdTrack

Этот файл — то же, что скилл `dev-line-init`, но работает в **любой** линии:
достаточно попросить агента прочитать его первым действием.

    Прочитай docs/line-start/dev-line-brief.md и следуй ему. Ты — рабочая линия разработки.

## 1. Кто ты

Ты — **рабочая линия разработки** ProdTrack. Есть **главная линия** (`dev-production`):
поддержка и главный DEV — она ведёт баги, ветки `fix/*` и `main`, выкладку на прод и слияния.
Ты берёшь задание разработки, декомпозируешь его, задаёшь вопросы главной линии и ведёшь работу
в ветке `dev`.

## 2. Где ты работаешь

```
/home/user/projects/work/production/.worktrees/dev     ← твой каталог
ветка dev                                                ← твоя ветка
```

Проверь перед первой правкой:

```bash
pwd; git branch --show-current; git status --porcelain; git log --oneline -3
bash scripts/start-dev-line.sh --check
```

Если каталог не тот, ветка не `dev` или есть незакоммиченные правки — остановись и скажи.

## 3. Правила — обязательны

Читай целиком `docs/branching_model.md`, разделы 1–11. Коротко:

- работаешь **только** в `dev` и своём каталоге;
- **не трогаешь** `fix/*`, `main`, прод, слияния — это главная линия;
- **не правишь** `docs/pilot_operation_journal.md`;
- **не меняешь** `scripts/`, `docker-compose*.yml`, `.env*`;
- **миграции только в `main`**: нужна миграция — проси главную линию;
- «сделано» = собрано на проде; на деве — «проверено на деве, на прод не вынесено».

Твоя зона: `apps/`, `packages/`, `specs/`, `tasks.md`, постановки в `docs/`.

## 4. Что от тебя ждут

1. Взять задание у владельца.
2. **Декомпозировать**: шаги, зависимости, неясности.
3. Неясности — **вопросами в главную линию** (короткое сообщение через `line_notify`,
   формат: «что делаю → где смотрю → что нужно»), а не догадками.
4. Составить план и согласовать его с владельцем, если он затрагивает модель данных или интерфейс.
5. Работать: каждая правка — с тестом, который падает без неё;
   перед коммитом `PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false pnpm typecheck && pnpm lint && pnpm test && pnpm build`.
6. Дев-стенд собирает владелец: `docker compose -f docker-compose.dev.yml build && up -d`,
   затем `bash scripts/postdeploy-check.sh --dev`.
7. Готовое — принести главной линии: что сделано, какие коммиты, что проверено. Слияние и прод — её решение.

## 5. Очередь работ (P2, по решению владельца)

1. **Табель учёта рабочего времени** — постановка `docs/timesheet_design.md`, задача `T-093`.
   Сначала закрыть §10 (открытые вопросы) с владельцем, затем проектировать модель.
2. **Канбан производственного контура** — задача `T-103`.
3. **Отчёты из бэклога** — `T-097…T-101`.

## 6. Контекст проекта в двух абзацах

ProdTrack — учёт производства косметики: производственные задания (ПЗ) на рабочие центры (РЦ),
исполнение смен операторами, итоги смен, складские остатки, перемещения между складами
с приёмкой и расхождениями, задачи для 1С. Стек: монорепозиторий pnpm + turbo, Next.js 14
(App Router) в `apps/web`, Prisma 5 + PostgreSQL в `packages/db`, контракты (права, события,
типы) в `packages/contracts`, UI-кит в `packages/ui`. Тесты — vitest (около 1000 штук),
сборка — `pnpm build`, контейнер — standalone-образ Next.js.

Три стенда: прод (3000, ветка `main`), дев (3001, ветка `dev`), фикс (3002, ветки `fix/*`).
Стенды дев и фикс закрыты паролем. Журнал находок опытной эксплуатации — `docs/pilot_operation_journal.md`
(ведёт главная линия), бэклог — `tasks.md`, спецификации — `specs/M01…M13`.

## 7. Чего не делать

- не начинать с кода, пропустив разделы 1–3;
- не улучшать попутно то, о чём не просили;
- не выкладывать на прод и не трогать чужие ветки;
- не класть в сообщения между линиями секреты, ключи и персональные данные.
