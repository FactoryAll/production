## Найденные дефекты

| Шаг | Критичность | Описание | Действие |
|-----|-------------|----------|----------|
| 7.2 | некритичный (искажение данных на экране) | В блоке «Длительность этапов» переходы документа и строки РЦ были смешаны в одну цепочку (этапы вида «Подтверждено → Получение подтверждено»), а запись «В работе → Завершено» дублировалась — одна с инициатором, вторая без него | Исправлено: длительности считаются и выводятся раздельно по сущностям, дублирующая запись хронометража в `buildShiftSummary` убрана. Добавлены 2 теста, один обновлён. Требуется повторная проверка шага 7.1 |
| 7.1 | некритичный (неполное отображение) | На экране «Хронометраж» таблица переходов документа заполнена, а блок «Длительность этапов» показывает «Записей по документу нет»: фильтр принимает короткий id (`3dfa5dab`), а расчёт длительностей искал точное совпадение с полным UUID | Исправлено: полный идентификатор и тип берутся из найденных записей; добавлены 2 regression-теста, обновлён существующий. Требуется повторная проверка шага 7.1 |
| 4.6 | некритичный (сортировка) | Список уведомлений был отсортирован не «новые сверху»: старые (03.10) оказывались выше новых (04.10). Причина — составной ключ сортировки: сначала «непрочитанные сверху», затем «новые сверху»; второй ключ в проде не соблюдался | Исправлено: сортировка только по времени, новые сверху. Тесты сортировки обновлены (3 файла). Требуется повторная проверка после деплоя |
| 4.4 | некритичный (неполное отображение) | В карточке Перемещения после согласования расхождения не было видно согласованное количество: показывался только факт при приёмке (6), хотя согласовано было 8. Данные при этом сохраняются верно — согласованное количество пишется в строку перемещения | Исправлено: столбец «Фактическое» переименован в «Факт при приёмке», в статусе «Согласовано» добавлен столбец «Согласованное количество». Добавлены 2 компонентных теста |
| 4.3 | некритичный (UX) | Счётчик непрочитанных в шапке не обновлялся на страницах, кроме «Уведомлений»: уведомление, пришедшее во время работы на списке или в карточке, появлялось только после перезагрузки | Исправлено: счётчик в шапке стал клиентским компонентом, подписанным на SSE-канал, и обновляется на любой странице без перезагрузки. Добавлены 5 компонентных тестов |
| 3.5 | некритичный (лишняя кнопка) | Под ролью **С1С** на списке ПЗ отображалась кнопка **«Создать ПЗ»**, хотя у роли есть только просмотр (право `production_order:create` — у НП). Кнопка была не обёрнута проверкой права | Исправлено: кнопка создания ПЗ выводится только при наличии `production_order:create`. Добавлен компонентный тест (под С1С кнопки нет, под НП есть). Проверено, что остальные кнопки списков и карточек (ПЗ и Перемещения) закрыты правами корректно |
| 1.4 (регресс) | критичный (блокировал сценарий) | После исправления дефекта №2 подтверждение получения ПЗ Оператором падало с сообщением «No role has permission production_order:confirm»: переходы ПЗ `CONFIRMED → IN_PROGRESS` и `IN_PROGRESS → COMPLETED` писали аудит с правом `production_order:confirm`, а у Оператора его больше нет — kernel-функция `writeAudit` отказывается атрибутировать роль (M13 BR-X) | Исправлено: переходы принимают право действия (`production_order:accept` при подтверждении получения, `production_order:report` при внесении итога, `production_order:confirm` при вводе за Оператора) — атрибуция снова корректна. Добавлены 2 regression-теста на атрибуцию и обновлены тесты-ожидания |
| 1.4 | критичный (лишние права у роли) | У роли **ОПР** в матрице прав было право `production_order:confirm`, которым закрыты подтверждение ПЗ, отмена ПЗ, ввод за Оператора и корректировка факта. По 00 §4.2 и Р-11/Р-12 это действия **только НП**: Оператор видел в карточке кнопки «Отменить ПЗ» и «Ввести за Оператора», и сервер выполнил бы их | Исправлено (решение владельца — фиксить сразу): право убрано у ОПР в матрице и в сиде, `accept`/`report`/`read_own` сохранены. Добавлены 3 теста матрицы и правка seed-теста. Нужна повторная проверка: под ОПР кнопок НП в карточке нет |
| 1.3 | критичный (белый экран, 500) | Переход по уведомлению EV-01 под Оператором давал серверную ошибку: карточка ПЗ требовала право `production_order:read`, которого у ОПР нет (у него `production_order:read_own`). Дефект существует с Фазы 2, но проявился в Фазе 4: Оператор — адресат EV-01/EV-08/EV-09, а M09 BR-2 требует перехода в целевой объект | Исправлено: карточка принимает `production_order:read` **или** `production_order:read_own`; ОПР видит только строки своего РЦ, чужое ПЗ → 404 вместо 500; роли без права чтения получают экран «Доступ запрещён». Добавлены 4 regression-теста. Нужна повторная проверка шага 1.3 |
