## Часть 0. Подготовка на VPS (выполняет пользователь)

### 0.1. Деплой релиза (проверенная процедура)

```bash
cd /opt/prodtrack
git pull origin main
git log -1 --oneline
docker compose down
docker compose build --no-cache
docker compose up -d
sleep 20
docker compose logs --tail=10 web
```

### 0.2. Миграции и сид (права `timing:read`)

```bash
cd /opt/prodtrack
docker compose exec -T web pnpm --filter @prodtrack/db db:migrate
docker compose exec -T web pnpm --filter @prodtrack/db db:seed
docker compose exec -T web pnpm --filter @prodtrack/db db:seed
```

Ожидаемо: обе команды сида завершаются без ошибок (повторный прогон проверяет идемпотентность).
Версия в футере после деплоя — `v1.2.0`. Соседей по серверу проверить:

```bash
curl -sI https://mes-midex.factoryall.ru || echo "mes-midex DOWN"
curl -sI https://tracker.factoryall.ru || echo "tracker DOWN"
```

### 0.3. Обновление конфига nginx для SSE (обязательно для real-time)

```bash
cp -r /etc/nginx/sites-enabled /root/nginx-backup-$(date +%F)
cd /opt/prodtrack
cp docs/nginx/prodtracker.factoryall.ru.conf /etc/nginx/sites-available/
nginx -t
systemctl reload nginx
```

Без этого шага канал уведомлений может буферизоваться прокси и обновление в реальном времени (сценарий 2) работать не будет.

### 0.4. Проверка пункта H: выгрузка уведомлений и расхождений из БД

```bash
cd /opt/prodtrack
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) AS notifications FROM notifications;"'
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT event_code, count(*) FROM notifications GROUP BY event_code ORDER BY event_code;"'
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) AS discrepancies FROM discrepancies;"'
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) AS audit_records, count(*) FILTER (WHERE archived) AS archived FROM audit_records;"'
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) AS timings FROM stage_timings;"'
```

Ожидаемо: таблицы существуют, счётчики растут после сценариев ниже. Вывод прислать — это закрывает открытый пункт **H** из Фазы 3.

## Часть 1. Подготовка тестовых данных

### 1.1. Пользователи (войти как admin/admin123 → /users)

| Логин | Роль | Примечание |
|-------|------|------------|
| `np` | NP | Начальник производства |
| `opr` | OPR | Оператор РЦ (должен быть привязан к сотруднику-оператору) |
| `ksgp` | KSGP | Кладовщик склада ГП |
| `usgp` | USGP | УСГП |
| `s1c` | S1C | Специалист 1С |

> При создании система ставит `mustChangePassword = true`; пароль по умолчанию совпадает с логином, при первом входе требуется смена.

### 1.2. Исходные данные

1. Убедиться, что на Производственном складе есть остаток ГП (категория GP). Если нет — выполнить короткий цикл Фазы 2 (ПЗ → подтверждение → итог смены).
2. Проверить на экране «Роли» (АДМ) наличие права **«Просмотр хронометража»** (`timing:read`) у всех ролей — подтверждает, что сид из шага 0.2 прошёл.
