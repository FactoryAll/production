# Отчёт «Потребление» — постановка (T-098)

Статус: **постановка**, код не начат. Ждёт ответов главной линии по §7.

Источник: бэклог `tasks.md` T-098 — «что и сколько списано на производство, по РЦ и
номенклатуре» (решение владельца 26.10.2026 «остальные в бэклог»).

## 1. Зачем

Потребление — это то, что цех **израсходовал**, чтобы выпустить продукцию: масса и
полуфабрикат списываются со склада в факте смены. Сейчас расход виден только как движение
склада по номенклатуре и категории остатка (`T-096 «Движение склада»` — строка «расход»),
но **не видно, какой РЦ сколько израсходовал**. Вопрос владельца — именно про цех:
«что и сколько списано на производство, по РЦ и номенклатуре».

## 2. Чего здесь нового — честно

| Что | Где уже есть | Что даёт этот отчёт |
|---|---|---|
| Расход по номенклатуре и категории остатка | **T-096**, колонка «расход» (движения `CONSUMPTION`) | не главное: показываем для сверки с T-096 |
| **Расход по РЦ** | нигде | главное: списание на конкретный цех |
| **Связь расхода с выпуском** | нигде | главное: сколько израсходовано на единицу выпуска (по категориям) |

Вывод: отчёт **не дублирует T-096** только пока в нём есть разрез по РЦ и связь с выпуском.
Если убрать РЦ — это будет второй «Движение склада», и делать его не нужно.

## 3. Определения

### 3.1. Единица

Строка потребления (`FactConsumption`): факт смены → номенклатура + **категория остатка**
(`stockCategory`: Масса / ПФ / ГП) + количество. Категория хранится в строке, а не выводится
из номенклатуры (ОПЭ-34): Масса и ПФ — разные остатки одной номенклатуры ГП.

Количество — в единицах номенклатуры (`Product.unit`). Складывать разные номенклатуры между
собой нельзя; поэтому и «общий расход» показывается **по номенклатуре**, а не одним числом.

### 3.2. Откуда берётся РЦ

Потребление привязано к факту, факт — к строке ПЗ, у строки есть РЦ (`workCenter`).
То есть РЦ потребителя — это РЦ строки, а не склад.

### 3.3. Дубли и старые данные — проверяемое свойство

ОПЭ-38: потребление пишется **один раз на линию** (на первый факт), иначе остаток списывался
бы дважды. Уникальность в схеме — `[productionFactId, productId]`, то есть **одна и та же
номенклатура может встретиться в двух фактах одной строки** (ГП и ПФ) в старых данных.

Отсюда правило отчёта — **то же, что уже принято для простоев** (T-101, ОПЭ-73/75), чтобы
не заводить третье правило на ту же ситуацию:

1. строки потребления группируются по **(строка ПЗ, номенклатура, категория остатка)**;
2. значение берётся с **основного факта** строки — того же, что определяет `pickPrimaryFact`
   (категория продукции строки, иначе первый из записанных). Так поступили с простоями,
   и в схеме это ровно тот факт, куда потребление пишется по ОПЭ-38;
3. если в основном факте строки потребления этой номенклатуры нет, а в другом есть — это след
   старых данных: значение берётся оттуда (максимум по дублям, а не сумма), а строка считается
   счётчиком **«строк с потреблением не в основном факте»**;
4. счётчик выводится под таблицей и в CSV — чтобы цифра объясняла происхождение, а не выглядела
   ни потерей, ни удвоением.

Функция `pickPrimaryFact` живёт в `lib/fact-worker-composition.ts` и уже используется составом,
простоями и этим отчётом — **второго правила «какой факт основной» не заводим**.

### 3.4. Период и отменённые

Период — по дате смены. Отменённые ПЗ не входят (строки не выполнялись). Незакрытые ПЗ
с фактом входят: потребление уже произошло.

## 4. Что показываем

**Разрез «По РЦ»**:

| Колонка | Значение |
|---|---|
| РЦ | код и название |
| Номенклатура | код и название, единица |
| Категория остатка | Масса / ПФ / ГП |
| Израсходовано | количество |
| Строк ПЗ | сколько строк списывали эту номенклатуру |
| Выпуск РЦ по категории | для контекста: сколько цех выпустил (Масса/ГП/ПФ) |

**Разрез «По номенклатуре»**: номенклатура, категория, израсходовано, в каких РЦ
(перечень кодов), сколько строк.

Итоги: по номенклатуре — общее количество; по РЦ — сколько строк с потреблением;
счётчик «строк с дублем потребления».

## 5. Экран, выгрузка, права

## 6. Проверяемые свойства (пойдут в тесты)

1. Одна и та же номенклатура в двух фактах строки не даёт двойного расхода (дедупликация
   по строке + номенклатура + категории остатка через `pickPrimaryFact`), и такие строки
   считаются счётчиком.
1а. **Показываем то, что лежит в данных** (урок ОПЭ-75): количество — это факт из
   `FactConsumption`, а не плановое потребление — планового в модели нет, поэтому путаница
   «план вместо факта», из-за которой правили карточку перемещения, здесь невозможна
   по устройству схемы. Это фиксируется тестом на выборку полей.
2. Расход по РЦ — это РЦ строки ПЗ, а не склад.
3. Разные номенклатуры не складываются в одно число.
4. Отменённое ПЗ не даёт расхода; факт на незакрытом ПЗ даёт.
5. Сумма по РЦ равна сумме по номенклатуре (одни и те же данные, два разреза).
