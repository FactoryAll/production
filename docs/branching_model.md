# Модель веток и стендов ProdTrack

Решение владельца продукта 24.10.2026. **Правила этого документа обязательны к исполнению** —
не рекомендации. Если правило мешает, его меняют явным решением, а не «на этот раз обойдём».

## Три пространства

| Пространство | Ветка | Порт | Домен | Назначение |
|---|---|---|---|---|
| **Прод** | `main` | 3000 | `prodtracker.factoryall.ru` | релиз, которым пользуются люди |
| **Дев** | `dev` | 3001 | `prodtracker-dev.factoryall.ru` | сложные сценарии и фичи, требующие много времени |
| **Фикс** | `fix/*` от `main` | 3002 | `prodtracker-fix.factoryall.ru` | мелкие правки: ошибки, баги, небольшие улучшения — на 1–2 дня |

Ветки — главное, стенды — следствие: стенд существует, чтобы проверить ветку, а не наоборот.

## Обязательные правила

### 1. Миграции создаются только в `main`

Это самое важное правило: разъехавшиеся истории миграций чинятся часами.

- Ветки `dev` и `fix/*` **не создают** файлов в `packages/db/prisma/migrations/`.
- Нужна миграция — она делается в `main`, затем `dev` и активная `fix/*` делают rebase на `main`.
- Если миграция уже есть на `dev` и не готова к `main` — это признак, что работа не «фикс» и не
  готова к релизу: она остаётся на деве, а фикс от неё не зависит.

### 2. Фикс живёт не дольше двух дней

Дольше — это уже фича, ей место в `dev`. Ветка `fix/*` не должна накапливать изменения:
чем дольше она живёт, тем дороже rebase и тем больше шансов разойтись с `dev`.

### 3. Результат фикса уходит и в прод, и в дев

Порядок строго такой:

1. `fix/*` от `main`, правка, тест, пайплайн.
2. Проверка на **фикс-стенде** (`bash scripts/postdeploy-check.sh --fix`).
3. Слияние в `main` → развёртывание прода.
4. `main` → `dev` (merge, не «потом как-нибудь»). Дев не должен отставать от исправлений.

### 4. Ни одна правка не едет на прод без проверки на стенде

- обычная работа: дев → прод;
- мелкий фикс: фикс → прод;
- исключений нет, даже для «одной строчки».

### 5. Стенды дев и фикс закрыты паролем

Стенд — не для пользователей: вход туда открыт только владельцу и разработчику.
Защита — **HTTP-пароль** (`/etc/nginx/.htpasswd-prodtrack`), а не список адресов:
адрес у провайдера плавает (26.10.2026 сменился с 185.253.183.61 на 185.253.180.220,
и стенд отдавал 403, пока список не поправили руками).

Шаблон сниппета — `docs/nginx/snippets/prodtracker-stand-auth.conf`, на сервере он лежит
в `/etc/nginx/snippets/prodtracker-dev-allow.conf` и `…-fix-allow.conf` (имена оставлены
прежними, чтобы не править сайты). Правило проверяется автоматически: раздел 9 в
`scripts/postdeploy-check.sh` — без учётных данных стенд обязан отвечать **401**.

### 6. Данные стендов не пересекаются

У каждого стенда своя база и свой `.env`: `.env` (прод), `.env.dev`, `.env.fix`.
Пароли и секреты свои — продовые значения на стендах запрещены.

### 7. Сборки не параллелятся

Один деплой за раз. Две одновременные сборки на 8 ГБ памяти упираются в потолок,
и первым падает то, что случайно оказалось самым большим (проверено 24.10.2026 на 4 ГБ).

### 8. Стенды собираются по одному, в порядке проверки

Одна команда не собирает несколько стендов сразу. Ошибка 25.10.2026 (ОПЭ-52): три стенда были
пересобраны одной цепочкой, и прод с девом получили тот же код одновременно с фиксом —
независимая проверка на фикс-стенде превратилась в формальность.

Правильный порядок:

1. `fix/*` → сборка **только** фикс-стенда (`docker-compose.fix.yml`) → проверка владельцем;
2. «ок» → merge в `main` → сборка **только** прода (`docker-compose.yml`);
3. `main` в `dev` → сборка **только** дева (`docker-compose.dev.yml`) — отдельным шагом,
   когда деву это нужно, а не «заодно с продом».

Причина правила: если все стенды получают код разом, откатить «только прод» нельзя, а дев перестаёт
быть независимой копией — он просто повторяет прод.

### 9. После любого слияния — проверить, что реально попало в `main`

Не полагаться на память о том, что «это ещё не слито». `--ff-only` и обычный merge умеют
протащить в `main` больше, чем ожидалось: 26.10.2026 слияние при разрешении конфликта журнала
утащило в `main` три доработки, и владельцу было сказано «они ждут переноса», хотя они уже
работали на проде два релиза.

Проверка — одна команда на каждую спорную правку:

```bash
git merge-base --is-ancestor <коммит> main && echo "в main ДА" || echo "в main НЕТ"
```

Или разом по названиям:

```bash
git log --oneline --all | grep -i "<что ищем>"
```

Правило простое: **прежде чем сказать «это на дев, но не на проде» — проверить командой.**
Цена ошибки — неверное представление владельца о том, что работает у пользователей.

### 10. Работа не считается сделанной, пока она не собрана на проде

Слияние в `main` — это **не** развёртывание. Прод обновляется только сборкой и перезапуском
контейнера; между `git merge` и работающим продом лежит `docker compose build && up -d`.

26.10.2026 случилось ровно это: роль ОТК и раздел «Отчёты» были слиты в `main`, проверены
на деве, и я сказал «standby» — а на проде их не было, потому что прод собирался с коммита
до них. Владелец поймал.

**«Сделано» значит:**

1. код в `main`, пайплайн зелёный;
2. прод собран (`build` + `up -d`), `scripts/postdeploy-check.sh` — без предупреждений;
3. для интерфейса — владелец увидел это на проде, а не только на стенде;
4. только после этого — «готово».

**Формулировки, которых не должно быть:** «сделано», «готово», «в работе не осталось» —
о том, что есть только на деве или только в `main`. Правильные слова: «на деве, на прод
не вынесено», «в `main`, сборка не делалась».

### 11. Два дерева, две линии: распределение задач и порядок работы

С 26.10.2026 работа идёт **двумя линиями**, каждая в своём рабочем каталоге (git worktree).
Один репозиторий, разные файлы на диске — так линии не затирают друг другу незакоммиченные правки.

| Линия | Каталог | Ветки | Чем занимается |
|---|---|---|---|
| **Главная линия** (`dev-production`) — поддержка и **главный DEV** | `/home/user/projects/work/production` | `fix/*`, `main` | баги, мелкие правки, слияния в `main`, выкладка на прод, ответы на вопросы рабочих линий |
| **Рабочая линия** (`dev-production-2`, `-3`, …) | `/home/user/projects/work/production/.worktrees/dev` | `dev` | новые модули: табель, канбан, отчёты, площадки |

**Подчинение:** рабочая линия не сливает ветки и не выкладывает на прод — она приносит готовое
главной линии и спрашивает разрешение на слияние. Главная линия решает и делает.

### Как открыть рабочую линию

1. Открыть новый чат на пресете **`dev-line`** (он лежит в `~/.dsh/.agent-presets/dev-line/` и
   отличается от `cordis` персоной рабочей линии и встроенным скиллом `dev-line-init`).
2. Первым сообщением вызвать скилл: **`/dev-line-init`**.
3. Скилл сам: прочитает правила, проверит каталог и ветку, сходит `start-dev-line.sh --check`,
   отправит главной линии сообщение о регистрации и покажет очередь работ.
4. Дальше линия спрашивает задание, декомпозирует его, уточняет неясности **вопросами
   в главную линию** и начинает работу в `dev`.

Второе дерево создаётся командой `git worktree add .worktrees/dev dev` (каталог в `.gitignore`,
общий `.git`, отдельные файлы). Внешний каталог для него недоступен: политика среды разрешает
запись только внутри рабочего каталога — поэтому дерево лежит внутри, а не рядом.

**Следствие, о котором надо помнить:** ветку `dev` занимает второе дерево, поэтому в дереве
поддержки `git checkout dev` завершится ошибкой `already used by worktree`. Синхронизация
и любые коммиты в `dev` делаются из второго дерева:

```bash
cd .worktrees/dev && git pull origin dev && git merge main && git push origin dev
```

#### Что кому принадлежит

| Что | Кто пишет |
|---|---|
| `docs/pilot_operation_journal.md` (записи `ОПЭ-*`) | **только поддержка** |
| `tasks.md`, `specs/`, постановки в `docs/` | **только разработка** |
| `scripts/`, `docker-compose*.yml`, `.env*` | поддержка (инфраструктура), изменения — через неё |
| код в своих ветках | каждая линия в своей |

Почему так: журнал и бэклог — самые конфликтные файлы, они уже дважды давали конфликты при слиянии.
Разные владельцы убирают эту причину целиком.

#### Приоритеты (жёсткая очередь)

1. **P0 — прод лежит или данные искажаются.** Всё останавливается: сначала фикс, потом всё прочее.
2. **P1 — баг на проде, но работать можно.** Идёт в фикс-полосу **вне очереди** относительно доработок:
   разработка не «доделывает фичу, а потом посмотрим».
3. **P2 — доработки и отчёты** (табель, канбан, новые отчёты). Разработка, ветка `dev`.
4. **P3 — бэклог** (`T-097…T-101` и им подобные): берётся по решению владельца, не самовольно.

#### Очерёдность выкладок

- **одна выкладка за раз** — команды даёт владелец, поэтому очередь под его контролем;
- прод собирается **только из `main`**; дев — из `dev`; фикс — из `fix/*`;
- линия разработки **не сливает ничего в `main`** и не касается `fix/*`: слияние и релиз — работа поддержки;
- выкладка фикса на фикс-стенд и выкладка фичи на дев-стенд могут идти в разное время, но не одновременно.

#### Как линии общаются

1. **Файлы** — постановки и бэклог в репозитории: разработка пишет, поддержка читает.
2. **git** — `git log main`, правило №9: прежде чем сказать «это не на проде», проверить командой.
3. **Короткая линия** — уведомление другой линии по её заголовку: одна строка о том, что случилось
   и где смотреть. Без тела отчётов, без секретов, без персональных данных: канал не шифруется
   и доступен любому процессу на машине.

Формат сообщения между линиями: «что сделано → где смотреть (путь или коммит) → что делать дальше».

## Рабочий цикл

**Мелкий фикс:**

```bash
git checkout main && git pull
git checkout -b fix/короткое-имя
# правка + тест, который падает без неё
pnpm typecheck && pnpm lint && pnpm test && pnpm build
git push origin fix/короткое-имя
# на сервере: checkout ветки, сборка фикс-стенда, проверка
bash scripts/postdeploy-check.sh --fix
# после проверки владельцем: merge в main, прод, затем main -> dev
```

**Долгая фича:**

```bash
git checkout dev && git pull
git rebase main          # перед началом: дев не должен отставать
# работа, ветка dev, проверка на дев-стенде
bash scripts/postdeploy-check.sh --dev
```

## Что нужно сделать один раз (установка третьего стенда)

1. DNS: A-запись `prodtracker-fix.factoryall.ru` → IP сервера.
2. `bash scripts/make-dev-env.sh --fix` — создаёт `.env.fix` со своими секретами.
3. `docker compose -f docker-compose.fix.yml build && docker compose -f docker-compose.fix.yml up -d`
4. nginx: `docs/nginx/prodtracker-fix.factoryall.ru.conf` → `/etc/nginx/sites-available/`, симлинк
   в `sites-enabled`, сертификат `certbot --nginx -d prodtracker-fix.factoryall.ru`.
5. Список разрешённых адресов: `/etc/nginx/snippets/prodtracker-fix-allow.conf` — по образцу
   `prodtracker-dev-allow.conf`.
6. Проверка: `bash scripts/postdeploy-check.sh --fix` — все разделы зелёные.

## Ресурсы сервера

С 24.10.2026: **4 ядра / 8 ГБ памяти / 60 ГБ диска / swap 1 ГБ** — этого хватает на три стенда
и одну сборку. Еженедельная чистка кэша сборки стоит в cron (иначе он дорастает до 20 ГБ
и диск кончается — проверено).
