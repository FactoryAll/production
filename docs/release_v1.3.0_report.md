## Проблемы и действия

1. **[закрыто, вне объёма релиза] `tracker.factoryall.ru` отвечает 502.** Диагностика выполнена 05.10.2026
   (вывод владельца продукта):

   | Признак | Значение | Вывод |
   |---------|----------|-------|
   | Контейнеры сервиса `tracker` в `docker ps -a` | отсутствуют (на хосте только `prodtrack_web`, `prodtrack_postgres`, `mes_frontend_prod`, `mes_backend`, `mes_db`) | сервис на этом хосте не запущен |
   | Upstream из nginx | `http://127.0.0.1:8000/` для `server_name tracker.factoryall.ru` | порт 8000 — не наш: `prodtrack_web` слушает `127.0.0.1:3000` |
   | Ошибка nginx | `connect() failed (111: Connection refused) ... upstream: "http://127.0.0.1:8000/"` | никто не слушает порт 8000 |
   | Первые ошибки по tracker в логе | 09:52 и 11:00 — **до** деплоя v1.3.0 (11:17) | 502 существовал до релиза |

   **Вывод:** 502 у `tracker.factoryall.ru` с релизом v1.3.0 не связан — сервис не запущен на хосте,
   nginx проксирует его на порт 8000, где нет слушателя, и ошибки в логе появились раньше деплоя.
   Это внешняя инфраструктура другого продукта, вне объёма Фазы 5; порт ProdTrack (3000) не затронут.
   Рекомендация владельцу: проверить, должен ли сервис `tracker` работать на этом хосте — запуск
   выполняется отдельно и к релизу ProdTrack не относится.

   Побочно в логе видны внешние сканирующие запросы (`GET /.env` на tracker) — к ProdTrack не относятся.

## Правки по итогам ручного тестирования (в `main`, до приёмки фазы)

Исправления внесены в ту же версию: фаза ещё не принята, релиз `v1.3.0` остаётся текущим,
патч-версия не выпускается. Правки попадут на прод при следующем редеплое.

| Находка | Что сделано | Коммит |
|---------|-------------|--------|
| **T-050, логика Перемещений** (критично: С1С видел данные до согласования количества) | Задача типа TRANSFER формируется только когда принимающая сторона подтвердила количество — `RECEIVED` или `RECONCILED`; в `SUBMITTED`/`DISCREPANCY` задача не создаётся, а преждевременно созданная убирается; на экране «1С» добавлено пояснение | `см. коммит ниже` |
| **Регресс T-073 при перепроверке** (критично: правка потребления стирала состав потребления и не пересчитывала остатки) | Причина: обёртка серверного действия не передавала потребление из формы, а сервер трактовал отсутствие поля как «потребления нет» — строки факта удалялись, движение по остатку при этом терялось. Исправлено: поле передаётся всегда, отсутствие поля означает «не править», номенклатура для движений грузится и по прежнему составу, потерять движение молча нельзя (ошибка вместо пропуска). Разбор формы вынесен в обычный модуль; добавлены регресс-тесты. Данные факта восстановлены на VPS | см. коммит ниже |
| **Колонка «Последнее изменение»** (вопрос по Р-18, решение владельца: вариант B) | Поле `lastChangedAt` больше не обновляется автоматически при любой записи задачи: время проставляет синхронизация с источником, а отметка «обработано» и её отмена его не трогают; время отметки видно в строке «Обработано: …» и в аудите. Добавлены тесты на оба действия | см. коммит ниже |
| **T-073** (пробел M04: в корректировке факта нельзя было изменить потребление, Р-18/Р-10) | В диалогах «Корректировать факт» и «Ввод за Оператора» появился блок потребления; серверное действие правит состав и количество, пересчитывает движения остатков Массы/ПФ по разнице (рост — списание, уменьшение — возврат) и пишет изменение в аудит «старое → новое»; покрыто тестами | см. коммит ниже |
| **T-072** (некритично: в диалогах исполнения выводился идентификатор) | В диалогах внесения итога и подтверждения получения показаны РЦ (код и наименование) и номенклатура строки; подпись номенклатуры в карточке задачи 1С приведена к стилю приложения; добавлены компонентные тесты | `b975040` |
