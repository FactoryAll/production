> пользователь выполняет и присылает результат, затем следующее. Этот файл — перечень сценариев и шагов,

## Часть 0. Подготовка на VPS (выполняет пользователь)

### 0.1. Деплой релиза

```bash
cd /opt/prodtrack
git fetch origin && git pull origin main
git log -1 --oneline
docker compose down
docker compose build --no-cache
docker compose up -d
sleep 25
bash scripts/postdeploy-check.sh
```

Ожидаемо: сборка проходит без ошибок, `postdeploy-check.sh` зелёный, версия в футере — **v2.0.0**
(значение `VERSION` встраивается на этапе сборки, поэтому `build --no-cache` обязателен).

### 0.2. Миграция и сид

```bash
cd /opt/prodtrack
docker compose exec -T web sh -lc 'prisma migrate deploy --schema=/app/packages/db/prisma/schema.prisma'
docker compose exec -T web sh -lc 'cd /app/packages/db && tsx prisma/seed.ts'
docker compose exec -T web sh -lc 'cd /app/packages/db && tsx prisma/seed.ts'
```

Ожидаемо: применяется миграция `20261006010000_add_employee_can_be_worker` (признак «Может привлекаться
работником РЦ»), оба прогона сида завершаются без ошибок и без дублей.

### 0.3. Проверка миграции на живой базе и соседей по серверу

```bash
cd /opt/prodtrack
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d employees"'
curl -sI https://mes-midex.factoryall.ru || echo "mes-midex DOWN"
curl -sI https://tracker.factoryall.ru || echo "tracker DOWN"
```

Ожидаемо: в описании таблицы `employees` есть колонка `canBeWorker` типа `boolean` со значением по
умолчанию `true`; оба соседних сервиса отвечают. Вывод прислать — это подтверждает применение
миграции к реальной базе.

## Часть 1. Тестовые данные

### 1.1. Пользователи

| Логин | Роль | Примечание |
|-------|------|------------|
| `admin` | ADM | администратор |
| `np` (или `test_multi_role`) | NP | начальник производства: ПЗ, перемещения, аудит, дашборд |
| `opr` | OPR | оператор РЦ, привязанный к сотруднику-оператору |
| `ksgp` | KSGP | кладовщик склада ГП |
| `test_s1c` | S1C | специалист 1С |

Для сценария 6 понадобится сотрудник **без** учётной записи с ролью ОПР (например, кладовщик) —
агент подготовит данные отдельным заданием, если такого сотрудника нет.

## Сценарий 1. Сводный дашборд: показатели и виджеты (T-054, M11 §8, Р-08)

**Шаг 1.1.** Войти под `np` (или другой ролью, кроме ОПР) и посмотреть, куда ведёт вход.
- Ожидаемо: после входа открывается экран **«Сводный дашборд»** (адрес `/dashboard`), в футере — `v2.0.0`.
- Прислать: скриншот верхней части экрана с футером.

**Шаг 1.2.** На экране дашборда найти четыре карточки показателей.
- Ожидаемо: видны «Производится (ПЗ текущей смены)», «Произведено за период», «В перемещении (открытые)»,
  «Принято на склад ГП за период»; в каждой — число и подпись (количество ПЗ и РЦ, число перемещений, число приёмок).
- Прислать: скриншот блока из четырёх карточек.

**Шаг 1.3.** Прокрутить экран и убедиться, что видны все виджеты Р-08.
- Ожидаемо: «Статусы ПЗ текущей смены по РЦ», «Объёмы произведённого по категориям», «Длительности этапов»
  (график и таблица) и таблица «Документы жизненного цикла».
- Прислать: скриншот виджета «Статусы ПЗ текущей смены по РЦ» и виджета «Длительности этапов».

**Шаг 1.4.** Переключить период на «30 дней» и нажать «Применить».
- Ожидаемо: значения «Произведено за период» и «Принято на склад ГП за период» меняются; показатели,
  привязанные к смене («Производится», статусы ПЗ по РЦ), не меняются.
- Прислать: скриншот карточек до и после переключения периода.

## Сценарий 2. Обновление дашборда в реальном времени (T-055, M11 BR-2)

**Шаг 2.1.** Открыть дашборд под `np` и, не закрывая вкладку, выполнить задание, которое агент выдаст
отдельным сообщением (создание документа).
- Ожидаемо: показатели на открытом экране обновляются **сами, без перезагрузки страницы**, в течение ~10 секунд.
- Прислать: два скриншота одного и того же окна — до и после появления документа.

## Сценарий 3. Список документов и фильтры (T-054, M11 BR-1, §8)

**Шаг 3.1.** В блоке фильтров выбрать тип «Перемещения», нажать «Применить».
- Ожидаемо: в таблице остаются только Перемещения; у каждой строки — тип, документ (ссылка), статус и возраст.
- Прислать: скриншот таблицы.

**Шаг 3.2.** Дополнительно выбрать статус «Принято».
- Ожидаемо: остаются только Перемещения в статусе «Принято»; если таких нет — сообщение
  «По заданным условиям документов нет».
- Прислать: скриншот таблицы или сообщения.

**Шаг 3.3.** Сбросить фильтры (тип «Все документы», статус «Все статусы»).
- Ожидаемо: первыми идут документы с наибольшим возрастом — значения в колонке «Возраст» убывают
  сверху вниз; формат «чч:мм», а от суток — с днями: «42 д 00:00».
- Прислать: скриншот таблицы.

## Сценарий 4. Оператор видит дашборд в разрезе своего РЦ (M11 §3, BR-3)

**Шаг 4.1.** Войти под `opr`, открыть «Дашборд» в меню.
- Ожидаемо: экран открывается (доступ есть у всех ролей), сверху — пояснение «Показатели — в разрезе ваших РЦ»;
  в виджете «Статусы ПЗ текущей смены по РЦ» — только строки своих РЦ.
- Прислать: скриншот пояснения под заголовком и виджета «Статусы ПЗ текущей смены по РЦ».

## Сценарий 5. Пункт меню «Роли» (T-069, M02)

**Шаг 5.1.** Войти под `admin`, найти пункт меню «Роли» и открыть его.
- Ожидаемо: пункт есть в меню, экран открывается, видна таблица ролей с числом пользователей и прав.
- Прислать: скриншот меню с пунктом и открытого экрана.

**Шаг 5.2.** Завершить сессию, войти под `ksgp` и открыть адрес `/roles` вручную.
- Ожидаемо: пункта «Роли» в меню нет; при прямом переходе — экран «Доступ запрещён» с указанием
  требуемой роли, а не белая страница и не 500.
- Прислать: скриншот меню и скриншот экрана «Доступ запрещён».

## Сценарий 6. Оператор ПЗ — только сотрудник с учётной записью ОПР (T-070, M03 §2)

**Шаг 6.1.** Под `np` открыть «ПЗ» → «Создать», раскрыть список «Оператор».
- Ожидаемо: в списке только сотрудники с активной учётной записью роли ОПР. Сотрудника без такой
  учётной записи (например, кладовщика или специалиста 1С) в списке нет.
- Прислать: скриншот раскрытого списка «Оператор».

---

## Сценарий 7. Признак «Может привлекаться работником РЦ» (T-071, M01 §4.1)

**Шаг 7.1.** Под `np` открыть НСИ → «Сотрудники» и найти колонку «Работник РЦ».
- Ожидаемо: у сотрудников значения «Да»/«Нет».
- Прислать: скриншот таблицы сотрудников.

**Шаг 7.2.** Открыть карточку сотрудника, снять переключатель «Может привлекаться работником РЦ» и
сохранить. Затем открыть форму ПЗ и раскрыть список «Работники (необязательно)».
- Ожидаемо: сотрудник со снятым признаком в списке работников отсутствует; с включённым — присутствует.
- Прислать: скриншот карточки сотрудника и скриншот списка работников в форме ПЗ.

## Сценарий 8. Перепроверка исправлений, ожидавших редеплоя (T-072, T-073)

Эти два дефекта исправлены 05–06.10.2026, но на развёрнутой версии ещё не перепроверялись.

**Шаг 8.1 (T-072).** Под `opr` открыть «Исполнение» и нажать «Внести итог» по любой строке.
- Ожидаемо: в диалоге видны код и наименование РЦ (например, «03 — 03.Тубировка крем») и продукция строки
  (код, наименование и единица), а не идентификатор вида «ПЗ по РЦ abc13ba9-…».
- Прислать: скриншот диалога.

**Шаг 8.2 (T-073).** Под `np` открыть карточку завершённого ПЗ → «Корректировать факт».
- Ожидаемо: в диалоге есть блок «Потребление»; можно изменить состав и количество потребления,
  сохранить и увидеть пересчёт остатков Массы/ПФ на экране «Остатки», а изменение — в аудите.
- Прислать: скриншот диалога с блоком потребления и скриншоты остатков до и после.

## Сценарий 9. Дашборд после тестирования (проверка целостности)

**Шаг 9.1.** Вернуться на дашборд под `np` и убедиться, что показатели соответствуют данным,
внесённым в сценариях 6–8.
- Ожидаемо: «Производится» отражает открытые ПЗ текущей смены, «Произведено за период» — внесённые итоги,
  «В перемещении» — открытые перемещения, «Принято на склад ГП» — приёмки; в списке документов видны
  созданные в ходе тестирования ПЗ и Перемещения с корректными статусами и возрастом.
- Прислать: скриншот дашборда целиком.
