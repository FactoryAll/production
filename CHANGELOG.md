## [1.3.0] - 2026-10-05

Фаза 5 «Данные для 1С»: рабочее место С1С (M12).

### Added
- **M12 T-050. Единая сущность `TaskForOneC` (Р-24).** Задача формируется автоматически в той же транзакции, что и переход документа: «Производство» — при завершении ПЗ (итог смены сформирован), с выпуском Массы, ГП и ПФ по РЦ и потреблением Массы/ПФ (Р-10, BR-2/BR-6); «Перемещение» — когда принимающая сторона подтвердила количество: при приёмке без расхождений или после согласования расхождения (решение владельца продукта 05.10.2026), со складами, строками ГП и количествами «заявлено/фактически принято» (BR-3); пока Перемещение отправлено, но не принято, данных для 1С нет. Данные всегда соответствуют последней версии источника (BR-9): синхронизация идемпотентна и при отсутствии изменений ничего не пишет (колонка «последнее изменение» не врёт: она отражает изменение данных источника, а отметка «обработано» и её отмена её не трогают — решение владельца продукта 06.10.2026), а изменение источника после отметки «обработано» возвращает задачу в «Ожидает» (решение владельца продукта 05.10.2026) — чтобы в 1С не остался документ по устаревшим данным. Добавлена миграция `20261006000000_add_task_for_one_c_unique`: уникальность «одна задача на источник» `(type, sourceId)`.
- **M12 T-051. Рабочее место 1С `/onec`.** Единый список задач обоих типов (Р-24) с серверным фильтром по типу и статусу, колонкой «последнее изменение» (Р-18) и карточкой задачи со структурированными данными для копирования в 1С (выпуск, потребление, строки Перемещения). Доступ определяется правом `onec:read` (00 §4.2 — С1С и АДМ); пункт меню «1С» видят только роли с этим правом, у остальных прямой переход даёт экран «Доступ запрещён».
- **M12 T-052. Отметка «обработано» и её отмена (BR-4, BR-5, BR-8, Р-17).** Отметку ставит только С1С (право `onec:process`); отмена требует обязательной причины и фиксируется в аудите двумя записями — смена статуса `PROCESSED → PENDING` и причина, с атрибуцией роли по праву действия (Р-23). Ошибка серверного действия показывается внутри диалога: он не закрывается до исправления причины.
- **M12 T-053. CSV-экспорт (Р-06, Р-24).** Единый файл по задачам обоих типов с учётом фильтров списка: UTF-8 с BOM (Excel не портит кириллицу), разделитель `;`, экранирование значений; одна строка файла — одна позиция документа (выпуск, потребление или строка Перемещения). Выгрузка ограничена 5000 задач.

### Changed
- Версия приложения в футере: `v1.3.0` (build arg `VERSION` в `docker-compose.yml` и `.env.example`).
- Справочник объектов аудита дополнен задачей для 1С: `TaskForOneC` отображается как «задача для 1С».

## [1.2.0] - 2026-10-03

Фаза 4 «Сквозные»: in-app уведомления (M09), хронометраж этапов (M10), аудит и история изменений (M13).

### Added
- **M09 T-044. Каталог событий EV-01…EV-10.** Единый источник истины по событиям (`packages/contracts/src/events.ts`): код события в форме спека и в форме Prisma-энума, название из 00 §5, заголовок уведомления, правило адресации, deep-link и валидация payload. Валидация EV-08 (Р-13): причина строго из пресета {ILLNESS, NO_SHOW, LEFT_SHIFT, OTHER} + обязательный непустой комментарий. Все 10 мест эмиссии переведены на каталог через диспетчер `apps/web/src/lib/events/notify.ts` (валидация → резолв адресатов → запись kernel-функцией `emitEvent`, T-059); дублирующая запись уведомлений удалена.
- **Deep-link на строку РЦ.** В карточке ПЗ у строк появился анкер `#line-<id>`, а уведомления EV-02 (подтверждение получения) и EV-08 (ввод за Оператора) ведут прямо на строку РЦ, как описано в M09 §7.
- **M09 T-045. Центр уведомлений.** Экран `/notifications`: фильтр «все/непрочитанные/прочитанные» (в строке запроса), непрочитанные сверху, кликабельные карточки с переходом в целевой объект, отметка прочитанности с фиксацией времени. Счётчик непрочитанных в шапке приложения, пункт меню «Уведомления» для всех ролей (M09 §3). Real-time через SSE-канал `/api/events/notifications` (счётчик непрочитанных + признак нового уведомления).
- **M10 T-046. Хронометраж.** Экран `/timing`: таблица статусных переходов с фильтром по типу документа и документу, расчёт длительностей этапов (включая отмену Р-12 и ввод за Оператора Р-11), текущий этап для незавершённых документов. Область видимости: ОПР — только свои РЦ (M10 §3), остальные роли — весь хронометраж. Новое право `timing:read` (все роли), пункт меню «Хронометраж».
- **M13 T-047. Аудит.** Экран `/audit`: фильтры по пользователю, типу и идентификатору объекта, периоду; журнал append-only (экран только читает записи). Вкладка «История изменений» в карточках ПЗ и Перемещения.
- **M13 T-049. Архивация (Р-16).** Записи старше 12 месяцев помечаются `archived = true` (не удаляются). Архив скрыт из обычных выборок всех ролей, кроме АДМ; флаг «показать архив» доступен только АДМ. Идемпотентный скрипт `pnpm db:archive-audit` (для cron на VPS) и кнопка «Архивировать старые записи» на экране аудита.
- **SSE-канал.** Keep-alive-кадры каждые 15 с (иначе nginx закрывает соединение по `proxy_read_timeout` на простое) и отдельный `location /api/events/` с `proxy_buffering off` в поставляемом конфиге `docs/nginx/prodtracker.factoryall.ru.conf` — без этого real-time за прокси не работает. Шаг обновления конфига описан в `docs/deploy_vps.md`.
- **T-057/T-058 для списков документов.** ПЗ и Перемещения переведены на серверную пагинацию и фильтр по статусу (в адресе страницы: `?status=…&page=…`); список ПЗ больше не загружает все задания сразу. Просмотр Перемещений теперь проверяется правом `transfer:read` (включая загрузку списка и карточки).
- **T-058. Серверный поиск по справочникам.** РЦ, причины брака, причины ввода за Оператора, склады, смены, номенклатура и сотрудники: поиск выполняется на сервере (`?q=`) без учёта регистра, фильтр активности (`?active=`) и постраничная выборка — тоже на сервере; локальная фильтрация в таблицах заменена формой поиска, добавлено состояние «ничего не найдено».
- **T-057. Пагинация списков.** Списки уведомлений, аудита и хронометража переведены на постраничную выборку (`skip`/`take`) без дополнительного `count`: признак следующей страницы определяется по «лишней» записи.

### Changed
- **Права роли С1С и просмотр Перемещений (решение владельца продукта, 03.10.2026).** Добавлено право `transfer:read` — просмотр Перемещений для НП, КСГП, УСГП, С1С и АДМ (раньше просмотр определялся правами на действия, отдельного права на чтение не было). Роли С1С выдано `production_order:read`, чтобы переход по уведомлениям EV-03/EV-05/EV-07 вёл в карточку ПЗ или Перемещения, а не на экран «Доступ запрещён». Создавать, подтверждать, принимать и согласовывать документы С1С по-прежнему не может; стартовая страница С1С после входа — «ПЗ» (было «Остатки»).
- **Адресаты уведомлений приведены к каталогу 00 §5** (T-044): EV-04 → КСГП и С1С; EV-05 → С1С; EV-06 → НП; EV-07 → С1С и УСГП; EV-09 → операторы назначенных РЦ; EV-10 → КСГП и С1С. Ранее уведомления уходили другим ролям (например, EV-04 — только КСГП, EV-07 — только КСГП, EV-10 — НП и КСГП).
- Заголовки уведомлений EV-03, EV-06 и EV-07 приведены к формулировкам каталога событий.
- **Р-09: обязательный лог расширен.** Приёмка и согласование расхождений теперь пишут аудит по каждой строке (изменение количества «старое → новое»), создание и согласование расхождения — отдельными записями; отмена Перемещения фиксируется действием `CANCEL`, как и отмена ПЗ (Р-12).
- Матрица прав: добавлено право `timing:read` (все роли); в `packages/contracts` добавлено значение `AuditAction.LOGIN_FAILED` — оно уже писалось в аудит при неудачном входе, но отсутствовало в контрактах.
- Версия приложения в футере: `v1.2.0` (build arg `VERSION` в `docker-compose.yml` и `.env.example`).

### Fixed
- **Дефекты ручного тестирования (11).** Подробное описание каждого — в `docs/release_v1.2.0_test_report.md`. Критичные: белый экран при переходе по уведомлению под Оператором, лишнее право `production_order:confirm` у роли ОПР и вызванный его исправлением регресс атрибуции аудита, потеря SSL-блока nginx при копировании шаблона конфига. Некритичные: кнопка создания ПЗ у С1С, невидимое согласованное количество, сортировка уведомлений, пустой блок длительностей, смешение переходов документа и строк, дублирующая запись хронометража, фантомные записи корректировки факта, активный фильтр типа у ОПР, неживой счётчик непрочитанных.- **Дефект №8 ручного тестирования.** На экране «Хронометраж» для роли ОПР фильтр «Тип документа» оставался активным и позволял выбрать «Перемещение», хотя область видимости Оператора — только ПЗ своих РЦ. Теперь у ОПР фильтр неактивен и содержит единственное значение «ПЗ».
- **Дефект №9 ручного тестирования.** Корректировка факта (Р-18) писала запись хронометража вида `REPORTED → REPORTED`, то есть «переход», не меняющий статус; в списке и в длительностях появлялись фантомные этапы «Итог внесён → Итог внесён». Записи убраны (корректировка фиксируется аудитом), а расчёт длительностей игнорирует записи без смены статуса — это чистит и исторические данные.- **Устойчивость хронометража к дублям переходов.** Дублирующие записи об одном переходе (следствие дефекта №7) уже накоплены в базе, поэтому расчёт длительностей схлопывает два одинаковых перехода, случившихся в пределах секунды, оставляя запись с инициатором.- **Дефект №7 ручного тестирования.** Хронометраж смешивал переходы документа и строк РЦ в одну цепочку этапов (получались бессмысленные этапы вида «Подтверждено → Получение подтверждено»), а переход ПЗ `IN_PROGRESS → COMPLETED` записывался дважды — второй раз без инициатора из `buildShiftSummary`. Теперь длительности считаются раздельно по сущностям (документ и каждая строка РЦ выводятся отдельными таблицами), а дублирующая запись убрана: переход пишет та сторона, которая его выполняет, с инициатором и правом действия.- **Дефект №6 ручного тестирования.** Блок «Длительность этапов» на экране «Хронометраж» оставался пустым, хотя записи переходов документа находились: в фильтре пользователь вводит короткий идентификатор (как он показан в таблице), а расчёт длительностей искал точное совпадение с полным UUID. Теперь полный идентификатор и тип документа берутся из найденных записей — это также закрывает доступ к длительностям документа вне области видимости (для Оператора — только свои РЦ).- **Дефект №5 ручного тестирования.** Список уведомлений сортировался составным ключом (сначала «непрочитанные сверху», затем «новые сверху»), и в проде порядок не соблюдался: старые уведомления оказывались выше новых. Теперь сортировка однозначная — строго по времени, новые сверху (M09 §11); непрочитанные отбираются фильтром.- **Дефект №4 ручного тестирования.** В карточке Перемещения в статусе «Согласовано» не было видно согласованное количество: столбец «Фактическое» показывал факт при приёмке из записи расхождения, а согласованное количество (оно хранится в строке перемещения, M08 §5) на экране не отображалось. Теперь столбец называется «Факт при приёмке», а в статусе «Согласовано» выводится отдельный столбец «Согласованное количество».- **Живой счётчик непрочитанных в шапке.** Раньше счётчик обновлялся только при переходе или перезагрузке: на других страницах (списки, карточки) уведомление, пришедшее во время работы, не отражалось, пока пользователь не обновит страницу. Теперь счётчик подписан на SSE-канал и обновляется сам на любой странице.- **Дефект №3 ручного тестирования.** Под ролью С1С на списке ПЗ отображалась кнопка «Создать ПЗ», хотя роль имеет только просмотр. Кнопка создания теперь выводится лишь при наличии права `production_order:create`.- **Регресс после исправления дефекта №2.** Подтверждение получения ПЗ Оператором падало с «No role has permission production_order:confirm»: переходы ПЗ `CONFIRMED → IN_PROGRESS` и `IN_PROGRESS → COMPLETED` фиксировались в аудите под правом `production_order:confirm`, которого у Оператора больше нет. Теперь переход принимает право действия: `production_order:accept` (подтверждение получения), `production_order:report` (внесение итога), `production_order:confirm` (ввод за Оператора); атрибуция роли в аудите (M13 BR-X) корректна.
- **Дефект №1 ручного тестирования.** Переход по уведомлению EV-01 под Оператором приводил к белому экрану с серверной ошибкой: карточка ПЗ требовала право `production_order:read`, которого у ОПР нет. Карточка теперь принимает `production_order:read` **или** `production_order:read_own`; Оператор видит только строки своего РЦ, чужое ПЗ отдаёт 404 вместо 500, роли без права чтения получают экран «Доступ запрещён».
- **Дефект №2 ручного тестирования.** У роли **ОПР** было право `production_order:confirm`, из-за чего Оператор мог подтверждать и отменять ПЗ, вводить данные за Оператора и корректировать факт — по 00 §4.2 и Р-11/Р-12 это действия только НП. Право у ОПР убрано (матрица и сид), права `accept`/`report`/`read_own` сохранены.
- Удалены устаревшие комментарии TODO (подтверждение получения ПЗ EV-02 реализовано в M04; редирект на смену пароля при первом входе реализован в `login/actions.ts`).

## [1.1.2] - 2026-10-03

## [1.1.1] - 2026-10-03
### Fixed
- **Критично:** страницы `/transfers` и `/transfers/[id]` отдавали 500 и падали с React error #482 — синхронный хелпер `transferStatusLabel` экспортировался из файла с директивой `'use server'`, из-за чего превращался в Server Reference и вызывался во время рендера («Server Functions cannot be called during initial render»). Хелперы статусов вынесены в `transfers/labels.ts`.
- **Критично:** белый экран «Application error: a server-side exception has occurred» после входа и после обязательной смены пароля у ролей КСГП, УСГП и С1С — `/dashboard` редиректил все роли на `/production-orders`, требующий права `production_order:read`. Добавлен ролевой лендинг `getLandingPath()` (НП/АДМ → ПЗ, ОПР → Исполнение, КСГП/УСГП → Перемещения, С1С → Остатки).
- **Критично:** при превышении остатка отправка Перемещения блокировалась сервером, но сообщение об ошибке не отображалось («ничего не происходит»): диалог закрывался до установки ошибки, а текст рендерился внутри него. Теперь диалог остаётся открытым, ошибка дополнительно выводится баннером на странице (карточка и список Перемещений).
- Запросы данных вынесены из файлов с `'use server'` в `transfers/queries.ts`, из auth-утилит убрана директива `'use server'` — серверные компоненты больше не вызывают Server Functions во время рендера.

### Added
- **Форма Перемещения:** под полем «Плановое количество» показывается доступный остаток выбранного продукта на складе-источнике (вместо «0.00»), при превышении поле подсвечивается красным и сохранение блокируется (BR-1 на клиенте).
- **Пункт меню «Перемещения»** для ролей с правами на перемещения (НП, КСГП, УСГП, АДМ).
- **Права НП:** ведение справочников — смены, номенклатура, сотрудники, РЦ, причины (`nsi:manage`); участие в согласовании расхождений (`transfer:reconcile`, M08 §3). Склады остаются за АДМ (`nsi:manage_warehouses`, Р-19).
