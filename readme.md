# ProdTrack

Система учёта производственных операций: производственные задания (ПЗ), исполнение смен
на рабочих центрах, складские остатки и перемещения, отчётность, уведомления.

Монорепозиторий: **pnpm + turbo**, приложение — **Next.js 14 (App Router)**,
данные — **PostgreSQL + Prisma**, контракты и права — отдельный пакет.

---

## Стек

| Слой | Что используется |
|---|---|
| Приложение | Next.js 14 (App Router), React 18, server actions |
| Данные | PostgreSQL 15, Prisma 5 (миграции + сид) |
| Общие контракты | `@prodtrack/contracts` — права, роли, статусы, события |
| UI | `@prodtrack/ui` — токены темы, компоненты |
| Тесты | Vitest (~1400 тестов), в том числе тесты экранов без базы |
| Сборка | turbo, standalone-образ Next.js в Docker |

## Быстрый старт (локально)

```bash
# 1. Зависимости
pnpm install

# 2. База: поднять PostgreSQL и указать строку подключения
cp .env.example .env          # отредактировать DATABASE_URL

# 3. Схема и данные
pnpm db:migrate
pnpm db:seed                  # сид печатает логин/пароль администратора ОДИН раз — сохраните

# 4. Приложение
pnpm dev                      # http://localhost:3000
```

**Про сид и пароли.** Пароля администратора в репозитории нет: сид берёт его из
`ADMIN_INITIAL_PASSWORD`, а если переменная не задана — генерирует случайный и печатает
в логе крупной рамкой. При первом входе система требует сменить пароль.
Тестовые учётные записи (`test_multi_role` и другие, чьи пароли лежат в репозитории)
создаются **только** при `SEED_TEST_USERS=true` — на стендах флаг включён в шаблонах `.env`,
на проде его нет и быть не должно.

**Проверки перед коммитом** — все четыре должны быть зелёными:

```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```

> Если pnpm ругается на проверку зависимостей перед запуском:
> `PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false pnpm <команда>`.

## Роли и права

Матрица прав живёт в одном месте — `packages/contracts/src/access.ts`. Сид сверяется с ней
двумя сторожевыми тестами, поэтому «права в базе» и «права в коде» не могут разъехаться молча.

Роли: `ADM` (администратор), `NP` (начальник производства), `OPR` (оператор),
`KSGP` / `USGP` (склад ГП / склады), `S1C` (специалист 1С), `OTK` (ОТК — просмотр и отчёты),
`GUEST` (только просмотр).

## Стенды и деплой

| Стенд | Порт | Ветка | Доступ |
|---|---|---|---|
| Прод | 3000 | `main` | открыт |
| Дев | 3001 | `dev` | по паролю |
| Фикс | 3002 | `fix/*` (или `main`) | по паролю |

Полный порядок развёртывания, nginx, сертификаты и защита стендов паролем —
`docs/deploy_vps.md`. Подъём на **новом** сервере и восстановление после потери VPS —
`docs/disaster_recovery.md`.

```bash
bash scripts/deploy.sh            # деплой с бэкапом
bash scripts/postdeploy-check.sh  # проверка после деплоя: 10 разделов
bash scripts/backup-db.sh         # дамп базы (вне репозитория)
bash scripts/backup-offsite.sh    # выгрузка дампа ЗА ПРЕДЕЛЫ сервера (обязательно)
```

## Процесс разработки

Модель веток, две линии (поддержка и разработка), приоритеты, порядок выкладки и правила
проверки — `docs/branching_model.md`. Кратко:

- `main` — только проверенное на стенде; миграции создаются только здесь;
- `dev` — работа линии разработки, отдельное рабочее дерево `.worktrees/dev`;
- `fix/*` — короткоживущие ветки правок;
- **работа не считается сделанной, пока не собрана на проде**;
- **в прод ничего не идёт, пока сценарии не проверены на дев-стенде**.
