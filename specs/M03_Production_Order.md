# Spec

## 1. Назначение и границы

**Вклад в North Star.** ПЗ — отправная точка жизненного цикла: оно определяет, «что и сколько производится» в текущую смену. Подтверждённое ПЗ немедленно становится видимым Операторам (через уведомление) и дашборду (M11), обеспечивая онлайн-видимость плана.

**In scope:**
- Создание и редактирование ПЗ (план на смену по РЦ).
- Назначение работников и Оператора на каждый РЦ.
- Подтверждение/сохранение ПЗ.
- Корректировка ПЗ (до ввода итога Оператором).
- Статусная модель ПЗ и строк ПЗ.

**Out of scope:**
- Внесение факта производства (M04).
- Расчёт остатков (M05).
- Отчётность (M06).

## 2. Глоссарий

- **Производственное задание (ПЗ)** — план на смену: для каждого РЦ указано, какой продукции и сколько произвести.
- **Строка ПЗ (РЦ-строка)** — элемент ПЗ, привязанный к одному РЦ: план продукции, назначенные работники, Оператор.
- **Оператор** — сотрудник, ответственный за выполнение задания на РЦ.
- **Подтверждение ПЗ** — действие НП, переводящее ПЗ из «Черновик» в «Подтверждено» и запускающее уведомление Операторов.

## 4. Доменная модель

### 4.1. Сущности

**Производственное задание (ProductionOrder)**
- `id`, `смена_id` (→ M01), `дата`, `статус`, `создал` (НП), `создано_в`, `подтверждено_в`.

**Строка ПЗ (ProductionOrderLine)**
- `id`, `пз_id`, `рц_id` (→ M01), `оператор_id` (→ M01), `работники[]` (→ M01), `план[]` (позиции: `номенклатура_id`, `количество`), `статус`.

### 4.2. Статусная модель

Статусы ПЗ (документ): `DRAFT → CONFIRMED → IN_PROGRESS → COMPLETED`, а также `CANCELLED` (см. 00_System_Overview §3.1).

Статусы строки ПЗ: `ASSIGNED → ACCEPTED → REPORTED`.

Переходы (событие + инициатор + блокировки):

| Переход | Событие | Инициатор | Блокировки |
|---------|---------|-----------|------------|
| `DRAFT → CONFIRMED` | ПЗ подтверждено (EV-01) | НП | Хотя бы одна строка с назначенным Оператором и непустым планом |
| `CONFIRMED → IN_PROGRESS` | Получение ПЗ подтверждено (EV-02) | Оператор | Первая строка перешла в `ACCEPTED` |
| `IN_PROGRESS → COMPLETED` | Итог смены внесён (EV-03) | Оператор | Все строки перешли в `REPORTED` |
| `CONFIRMED → COMPLETED` | Итог смены внесён (EV-03) | Оператор | ПЗ содержит ровно один РЦ (Р-04) |
| `DRAFT → CANCELLED`, `CONFIRMED → CANCELLED` | ПЗ отменено (EV-09) | НП | До первого `REPORTED` (Р-12) |
| `ASSIGNED → ACCEPTED` | Получение ПЗ подтверждено (EV-02) | Оператор | Строка в `ASSIGNED`, ПЗ в `CONFIRMED`/`IN_PROGRESS` |
| `ACCEPTED → REPORTED` | Итог смены внесён (EV-03) | Оператор | Строка в `ACCEPTED` |
| `ASSIGNED → REPORTED` | Смена закрыта за Оператора (EV-08) | НП | Ввод за Оператора при объективных причинах (Р-11) |

Правило закрытия (Р-04): при РЦ > 1 `REPORTED` возможен только после `ACCEPTED`; `COMPLETED` — только когда все строки `ACCEPTED` и `REPORTED`.

Правило корректировки: ПЗ и строки корректируются только пока ни одна строка не в `REPORTED`.

## 5. Сценарии (use cases)

**UC-M03-1. Создание ПЗ.**
- Когда НП открывает «Производственные задания» → нажимает «Создать» → система создаёт ПЗ в статусе `DRAFT` с привязкой к смене.
- НП добавляет строки: выбирает РЦ, номенклатуру, количество, назначает работников и Оператора → сохраняет → система сохраняет строки в `ASSIGNED`.

**UC-M03-2. Подтверждение ПЗ.**
- Когда НП завершил составление → нажимает «Подтвердить» → система проверяет полноту (BR-1) → переводит ПЗ в `CONFIRMED` и генерирует EV-01.
- Альтернатива: ПЗ неполное → система блокирует подтверждение с указанием незаполненных строк.

**UC-M03-3. Корректировка ПЗ.**
- Когда НП редактирует ПЗ в `DRAFT`/`CONFIRMED`/`IN_PROGRESS` → система сохраняет изменения.
- Исключение: хотя бы одна строка в `REPORTED` → система блокирует корректировку (BR-2).

**UC-M03-4. Ввод за Оператора (Р-11).**
- Когда Оператор не может внести итог по объективным причинам → НП открывает строку РЦ → выбирает причину из пресета {болезнь, неявка, ушёл во время смены, прочее} (Р-13) → вводит обязательный комментарий → устанавливает статус `REPORTED` → система переводит строку в `REPORTED`, генерирует EV-08 (payload: `причина_код`, `комментарий`) и EV-03, фиксирует в аудите.

**UC-M03-5. Отмена ПЗ (Р-12).**
- Когда НП отменяет ПЗ в `DRAFT`/`CONFIRMED` (до первого `REPORTED`) → система переводит ПЗ в `CANCELLED`, генерирует EV-09, фиксирует в аудите.

**UC-M03-6. Корректировка факта после закрытия (Р-18).**
- Когда ПЗ в `COMPLETED` и требуется исправить факт → НП открывает строку РЦ → через механизм «ввод за Оператора» (Р-11) выбирает причину из пресета + комментарий → помечает «корректировка после закрытия» → сохраняет → система обновляет факт, фиксирует в аудите (кто, когда, старое→новое).

## 6. Бизнес-правила

- **BR-1.** ПЗ подтверждается только при наличии хотя бы одной строки с назначенным Оператором и непустым планом. (Этап: Планирование.)
- **BR-2.** Корректировка ПЗ запрещена после ввода Оператором итога (первая строка в `REPORTED`). (Этап: Планирование/Производство.)
- **BR-3.** На каждый РЦ назначается ровно один Оператор. (Этап: Планирование.)
- **BR-4.** План строки может содержать только номенклатуру из M01. (Этап: Планирование.)
- **BR-5.** ПЗ привязано к одной смене. (Этап: Планирование.)
- **BR-6.** Подтверждать ПЗ может только НП. (Этап: Планирование.)
- **BR-7.** Валидация строки ПЗ: Масса — только на РЦ 01/02; номенклатура ГП — только на РЦ 03–12 (Р-02). (Этап: Планирование.)
- **BR-8.** Закрытие ПЗ: при РЦ = 1 допустим прямой `CONFIRMED → COMPLETED`; при РЦ > 1 `COMPLETED` только когда все строки `ACCEPTED` и `REPORTED` (Р-04). (Этап: Производство.)
- **BR-9.** Ввод за Оператора: НП вправе установить строке `REPORTED` при объективных причинах; причина выбирается из пресета {ILLNESS, NO_SHOW, LEFT_SHIFT, OTHER} + обязательный комментарий (Р-13); фиксируется в аудите (Р-11). (Этап: Производство.)
- **BR-10.** Отмена ПЗ: `CANCELLED` из `DRAFT`/`CONFIRMED` до первого `REPORTED`; инициатор НП (Р-12). (Этап: Планирование.)
- **BR-11.** Корректировка факта после `COMPLETED` — только НП через «ввод за Оператора» с обязательной причиной и пометкой «корректировка после закрытия»; каждая правка — в аудит (Р-18). (Этап: Итог смены.)

## 7. События и уведомления

- **Генерирует:** EV-01 «ПЗ подтверждено» (при `DRAFT → CONFIRMED`), EV-08 «Смена закрыта за Оператора» (Р-11), EV-09 «ПЗ отменено» (Р-12).
- **Потребляет:** EV-02 «Получение ПЗ подтверждено» (обновляет статус ПЗ/строки), EV-03 «Итог смены внесён» (обновляет статус ПЗ/строки).
- **Уведомляет:** EV-01 → Операторы назначенных РЦ; EV-08 → Оператор РЦ, С1С; EV-09 → Операторы назначенных РЦ (in-app, переход в карточку ПЗ).

## 8. Требования к интерфейсу

- Экран «Производственные задания» — список ПЗ с фильтром по смене/статусу.
- Карточка ПЗ — шапка (смена, дата, статус) + таблица строк (РЦ, Оператор, работники, план).
- Форма строки — выбор РЦ, номенклатуры, количества, назначение работников и Оператора.
- Кнопка «Подтвердить» — активна только при полноте ПЗ.
- Режим редактирования недоступен при наличии строки в `REPORTED`.

## 9. Хронометраж

Фиксируются переходы (связь с M10):
- `DRAFT → CONFIRMED` (время подтверждения ПЗ).
- `CONFIRMED → IN_PROGRESS` (время первого подтверждения получения).
- `IN_PROGRESS → COMPLETED`, `CONFIRMED → COMPLETED` (время завершения смены).
- `DRAFT → CANCELLED`, `CONFIRMED → CANCELLED` (время отмены, Р-12).
- Строка: `ASSIGNED → ACCEPTED`, `ACCEPTED → REPORTED`, `ASSIGNED → REPORTED` (ввод за Оператора, Р-11).

## 10. Критерии приёмки

- [ ] НП создаёт ПЗ с несколькими РЦ, назначает Операторов и работников.
- [ ] Подтверждение блокируется при неполном ПЗ.
- [ ] Подтверждение генерирует EV-01 и уведомляет Операторов.
- [ ] Корректировка блокируется после первого `REPORTED`.
- [ ] Статусная модель ПЗ и строк согласована с 00_System_Overview.
- [ ] Валидация строки по Р-02 (Масса на 01/02, ГП на 03–12) работает.
- [ ] Закрытие по Р-04 (прямой переход при 1 РЦ; все ACCEPTED+REPORTED при >1) работает.
- [ ] Ввод за Оператора требует причину из пресета + комментарий (Р-13).
- [ ] Корректировка факта после COMPLETED — только НП с пометкой и аудитом (Р-18).
- [ ] Ввод за Оператора (Р-11) и отмена ПЗ (Р-12) работают с аудитом и уведомлениями.

## 11. Открытые вопросы

1. [ДОПУЩЕНИЕ] Может ли ПЗ содержать несколько РЦ (принято: да, многострочный документ).
2. [ДОПУЩЕНИЕ] Один Оператор на РЦ (принято: ровно один).
3. [ДОПУЩЕНИЕ] План строки — список позиций номенклатуры с количеством (принято: да).
4. [ДОПУЩЕНИЕ] Перечень «объективных причин» для ввода за Оператора (Р-11) — не задан; требуется уточнение.
